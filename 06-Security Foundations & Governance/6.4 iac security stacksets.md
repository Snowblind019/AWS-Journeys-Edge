## What I built

- Ran the **validity gate**: cfn-lint caught spec violations (invalid enums, wrong types, a typo'd resource type, an out-of-range value), which are validity issues, not security.
- Ran the **security gate**: wrote a Guard policy that failed a valid-but-insecure template (no encryption, SSH open to the world) with a non-zero exit code, then fixed the template to pass.
- **Unit-tested** the rules and generated scaffolding with `rulegen`.
- Bridged to **server-side enforcement** with CloudFormation Hooks (a Guard-backed Hook is a proactive control), and rolled a baseline out with a **service-managed StackSet** to an OU.

The point was that IaC security is a chain of gates. cfn-lint checks whether a template will deploy, cfn-guard checks whether it should, a CloudFormation Hook makes the policy unskippable server-side, and StackSets push the validated baseline across the org, where the service-managed model auto-deploys to new accounts.

## The model this proves

IaC security is a pipeline of gates, and each answers a different question.

| Gate | Tool | Checks | Skippable? |
|---|---|---|---|
| Validity | cfn-lint | will it deploy (spec correctness) | editor and CI |
| Security policy | cfn-guard | should it deploy (your invariants) | yes, someone can bypass CI |
| Server-side backstop | CloudFormation Hook (Guard-backed) | policy at the CFN API before provisioning | no, and it equals a proactive control |

The same policy lives in three places along the path: cfn-lint-adjacent in your editor, cfn-guard in CI, and a Hook at the CloudFormation API as the unskippable backstop. A Guard-backed Hook is exactly what a Control Tower proactive control is under the hood, which is why it inherits the same CloudFormation-only limit from 6.3.

Then the rollout. A StackSet deploys one template across many accounts, with two permission models:

| | Self-managed | Service-managed |
|---|---|---|
| IAM roles | you create the admin and execution roles | CloudFormation manages them |
| Targets | specific account IDs | Organizations OUs or the root |
| Org integration | none | trusted access required |
| Auto-deployment | no | yes, new accounts in a target OU get it automatically |
| Use when | targets are outside your org, or manual control | targets are in your org, hands-off governance |

## What each demo proved

**cfn-lint: the validity gate.**
cfn-lint catches spec violations (an invalid enum, a wrong case, a wrong property type, a typo'd resource type, an out-of-range value), which are validity issues, not security. A template that will not even deploy never reaches your policy checks, so this is gate one. Errors are E, warnings are W, informational is I, and suppressing security-relevant warnings to make a pipeline green is exactly what an auditor looks for.

**cfn-guard: the security gate.**
A template can pass cfn-lint and still be insecure (no encryption, SSH open to 0.0.0.0/0), because invalidity is not the problem. A Guard policy with custom violation messages fails that template with a non-zero exit code, which is what fails a CI build, and fixing the template to add encryption, a public access block, and internal-only SSH flips it to a clean pass with nothing deployed and nothing billed.

**Test and generate the rules.**
Rules are code, so you unit-test them with expectations (open SSH should FAIL, internal SSH should PASS), and `rulegen` bootstraps a policy from a known-good template. But `rulegen` emits a rule for essentially every property, which is too strict and brittle, so you treat it as scaffolding to trim to the handful of security invariants you mean to enforce.

**Hooks: the server-side backstop.**
Client-side Guard in CI is skippable, since someone can deploy a template that never went through the pipeline, so CloudFormation Hooks run the same policy server-side at the CloudFormation API before resources are provisioned. A Guard-backed Hook is exactly what a Control Tower proactive control is, so it inherits the same limit: it only catches CloudFormation, not a resource made from the console or CLI, which still needs Config or an SCP.

**StackSets: rollout across the org.**
A StackSet deploys one template as stack instances across many accounts and Regions from a single operation, and the two permission models are the exam item. Self-managed has you create the admin and execution roles and target specific account IDs, while service-managed has CloudFormation manage the roles, targets Organizations OUs, requires trusted access, and auto-deploys to new accounts added to a target OU.

## The subtle one: validity versus security, the Hook limit, and StackSets distinctions

Several tested edges here.

**cfn-lint and cfn-guard answer different questions.** cfn-lint checks validity, whether the template will deploy, and cfn-guard checks security policy, whether it should. A template passing cfn-lint is not secure, and suppressing security warnings to green a pipeline is an audit red flag.

**The `when ... exists` guard is load-bearing in Guard rules.** A rule that queries a missing property without a `when` clause can error or produce confusing results instead of a clean PASS or FAIL, so you wrap queries in `when %x !empty` and `when PropName exists`, and `cfn-guard parse-tree` shows the structure Guard sees.

**The Hook inherits the proactive-control limit.** A Guard-backed Hook only evaluates CloudFormation, so a resource made through the console, CLI, or Terraform bypasses it, and you cover those with a detective control (Config) or a preventive control (SCP), the identical 6.3 limitation from the IaC side.

**StackSets self-managed versus service-managed.** Self-managed means you create the roles and target account IDs, service-managed means CloudFormation manages the roles, targets OUs, needs trusted access, and auto-deploys to new accounts. Auto-deployment is the service-managed superpower.

**StackSets versus Account Factory.** Account Factory creates accounts, StackSets deploy resources into accounts, and they complement rather than replace each other. "Standardize new account creation" is Account Factory, and "deploy the same Config rules or GuardDuty enablement into 80 accounts" is StackSets. Pairing Account Factory with a service-managed auto-deploying StackSet is how every new account is vended governed and receives the baseline automatically.

## Exam relevance

- **cfn-lint checks validity (will it deploy), cfn-guard checks security policy (should it deploy).** A valid template can still be insecure, and suppressing security warnings to pass CI is an audit flag.
- **Guard rules are code:** unit-test them with `cfn-guard test`, treat `rulegen` output as scaffolding to trim, and wrap queries in `when ... exists`.
- **The same policy runs in the editor, in CI (cfn-guard, skippable), and as a CloudFormation Hook (server-side, unskippable).** A Guard-backed Hook is a Control Tower proactive control.
- **A Hook only catches CloudFormation**, so cover console, CLI, and Terraform paths with Config (detective) or an SCP (preventive).
- **StackSets deploy one template across many accounts.** Self-managed uses roles you create and account-ID targets, service-managed uses CloudFormation-managed roles, OU targets, trusted access, and auto-deployment to new accounts.
- **StackSets deploy resources into accounts, Account Factory creates accounts.** Pair them so new accounts are governed and baselined automatically.
