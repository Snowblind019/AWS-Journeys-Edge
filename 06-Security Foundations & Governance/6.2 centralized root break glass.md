# 6.2 — Centralized Root, Delegated Admin & Break-Glass

**Domain 6: Security Foundations and Governance (14%)**

## What I built

- Enabled **centralized root access** (the two features plus IAM trusted access) and hit the trap that a root-deny SCP silently breaks `sts:AssumeRoot`.
- Registered a **delegated administrator** so the security account, not the management account, runs root administration, the same pattern that runs every security service.
- Deleted a member account's **root credentials** centrally and audited zero active root credentials without ever logging in as root.
- Performed a real **root-only task** through a task-scoped session (unlocking a deny-all bucket policy), and confirmed the session could do nothing else.
- Worked the **break-glass design** and the list of root-only tasks that centralized access does not cover.

The point was that Domain 6's governance move is to remove standing root credentials and run privileged work through delegated admin and task-scoped sessions, with break-glass reserved for the handful of root-only tasks that cannot be delegated. The reflex the exam tests is delegated admin for everything, and the trap is an SCP that looks like good hygiene but disables the safe path.

## The model this proves

Centralized root access turns root from a standing liability into an on-demand, scoped, audited capability, and this subdomain is the governance posture around it.

- **Enable the two features, and watch for the SCP trap.** A root-deny SCP blocks `sts:AssumeRoot` and silently disables centralized sessions.
- **Delegated admin is the universal pattern.** The same `register-delegated-administrator` call, with a different service principal, runs GuardDuty, Security Hub, Macie, Detective, Inspector, IAM Access Analyzer, Config aggregation, Audit Manager, and Firewall Manager from a security account rather than the management account.
- **Delete standing root credentials, secure by default.** New accounts ship with no root credentials, which cuts both ways.
- **Perform root-only tasks through task-scoped sessions**, which are the ceiling (the 2.7 model, applied).
- **Reserve break-glass for the root-only tasks centralized access does not cover.**

| Centralized root sessions cover | Actual root sign-in still required |
|---|---|
| unlock S3 or SQS resource policies | change account name, email, or root password |
| manage root credentials (delete, create, audit) | restore IAM user permissions after a lockout |
| | change or cancel the AWS Support plan |
| | close the account |
| | register as an RI Marketplace seller |
| | sign up for AWS GovCloud (US) |
| | enable MFA Delete on an S3 bucket |

## What each demo proved

**Enable centralized root: mind the SCP trap.**
Enabling trusted access for IAM and the two features (RootCredentialsManagement, RootSessions) turns the capability on. The trap is a "lock down root" SCP that denies all root actions, because it also blocks `sts:AssumeRoot` and silently disables centralized sessions. If sessions fail with access denied, look for a root-deny SCP and add an allow or exception for `sts:AssumeRoot`. It is a favorite trap because the SCP looks like good hygiene while quietly disabling the safe path.

**Delegated admin: the reflex for every security service.**
Registering the security account as delegated administrator moves root administration off the management account, and the same call runs every security service from that account. If an answer choice has you administering a security service from the management account, it is almost always wrong.

**Delete root credentials and audit.**
Deleting a member account's root password, keys, certs, and MFA centrally, then auditing with a read-only `IAMAuditRootUserCredentials` session, demonstrates zero active root credentials without ever logging in as member root. New accounts then ship with no root credentials, secure by default, though that means no root password and no recovery until you re-enable it, which will break a process that expected fresh-root login.

**Perform a scoped root task.**
A deny-all bucket policy locks out even the account admin, and pre-2024 the only fix was signing in as that account's root. A task-scoped root session with `S3UnlockBucketPolicy` deletes the policy, and the session can do nothing else, because the task policy is the ceiling. This is the answer to a locked bucket policy, not "recover the root password."

**Break-glass design.**
Break-glass is the procedure for when the normal path fails (Identity Center down, IdP unreachable, roles locked out). The design is a separate rarely-used identity with vaulted split-custodian credentials, hardware MFA on the irreducible management-account root, tight alarming and auditing (EventBridge on root and `AssumeRoot` to SNS), and least privilege even here, preferring a scoped role over standing root.

## The subtle one: the SCP trap, the delegated-admin reflex, secure-by-default, and what root sessions do not cover

Several tested edges here.

**The root-deny SCP breaks `sts:AssumeRoot`.** A "lock down root" SCP that denies all root actions looks like good hygiene but disables centralized root sessions, so you add an allow or exception for `sts:AssumeRoot`.

**Delegated admin is reflexive for every security service.** GuardDuty, Security Hub, Macie, Detective, Inspector, Access Analyzer, Config, Audit Manager, and Firewall Manager all run from a security account via delegated admin, and administering any of them from the management account is almost always wrong.

**Secure by default cuts both ways.** After enabling root credentials management, new member accounts have no root password and are not eligible for recovery until you re-enable it, which is intended, not a bug, and it will break a process that expected to log in as a fresh account's root.

**Centralized sessions do not cover everything.** Task-scoped sessions handle the common root tasks (unlock S3 and SQS policies, manage root credentials), but a specific list still requires an actual root sign-in and is exactly what break-glass exists for: changing the account name, email, or root password, restoring IAM user permissions after a lockout, changing or cancelling the Support plan, closing the account, registering as an RI Marketplace seller, signing up for GovCloud, and enabling MFA Delete on an S3 bucket.

## Exam relevance

- **Enable centralized root with the two features and IAM trusted access.** A root-deny SCP blocks `sts:AssumeRoot` and disables the safe path, so allow or except `sts:AssumeRoot`.
- **Delegated admin is the universal pattern for every security service.** Administering a security service from the management account is almost always wrong.
- **Deleting member root credentials centrally gives zero standing root credentials**, and new accounts are secure by default (no root password, no recovery until re-enabled), which is intended behavior.
- **A task-scoped root session is the answer to a locked bucket or queue policy** (`S3UnlockBucketPolicy`, `SQSUnlockQueuePolicy`), and the task policy is the session's ceiling.
- **Break-glass is a separate, vaulted, alarmed, least-privilege identity**, with hardware MFA on the irreducible management-account root and alarms on all root and `AssumeRoot` activity.
- **Centralized root sessions do not cover the root-only tasks that need an actual root sign-in** (account name, email, or password, restore IAM after lockout, Support plan, close account, RI Marketplace seller, GovCloud, MFA Delete on S3). Those are the break-glass cases.
