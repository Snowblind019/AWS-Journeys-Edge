# 6.5 — Cross-Account Sharing & Firewall Manager

**Domain 6: Security Foundations and Governance (14%)**
**Companion to:** `scs-c03-lab-6_5-sharing-firewall-manager.md` (the runnable lab). This file records what was built and *why each answer wins*, one level deeper than the lab's terse lines.

**Cost:** about $0 for what got built. Part A (RAM) is free, and Parts B and C are decision drills. Part D (Firewall Manager) is scenario only and is not free, since it bills per policy per Region per month plus the underlying WAF, Shield, and Network Firewall costs, so do not stand it up.

---

## What I built

- Enabled org sharing and shared an **infrastructure resource** (a managed prefix list standing in for a subnet) into the org with a **RAM resource share**, which needed no invitation acceptance because the targets were in the org.
- Worked the **decision drill**: launch EC2 into a shared subnet (RAM), grant an analytics role read on one bucket and its KMS key (resource-based policy, two-sided), and let dev teams self-deploy approved stacks without underlying permissions (Service Catalog with a launch constraint).
- Studied **Service Catalog's pieces** and **Firewall Manager's** prerequisites, policy types, and the one thing only it does, both scenario-only.

The point was two skills, one question: what exactly are you sharing or enforcing, and to whom. RAM shares infrastructure, a resource-based policy grants a principal access to one data resource, Service Catalog hands out governed self-service, and Firewall Manager is the org-wide network enforcement layer. Picking the wrong tool is wrong even when it technically works.

---

## The model this proves

Four tools, four jobs, and the exam decides between them on what you are sharing or enforcing and to whom.

| Tool | What you share or enforce | To whom | Free? |
|---|---|---|---|
| AWS RAM | infrastructure resources (subnet, transit gateway, prefix list, Resolver rules, License Manager, Capacity Reservations) | accounts, OUs, or the org | yes |
| Resource-based policy | one data resource (S3, KMS, SQS, SNS, Lambda, Secrets Manager) | a specific principal | yes |
| Service Catalog | approved products, governed self-service | teams via shared portfolios | catalog free, launched resources cost |
| Firewall Manager | WAF, Shield Advanced, security group, Network Firewall, DNS Firewall policies | all in-scope accounts, auto-applied to new resources | no, bills per policy |

The distinctions that carry it: RAM shares an infrastructure resource so another account can use it, not API access to data. A resource-based policy grants a specific principal access to one data resource, and cross-account it needs both sides. Service Catalog gives governed self-service where users deploy approved products without the underlying permissions. Firewall Manager centrally deploys network protections and auto-applies them to new resources and accounts.

## What each demo proved

**RAM: share an infrastructure resource.**
Enabling org sharing once and creating a resource share hands a prefix list (or a subnet, transit gateway, or Resolver rule) to accounts, OUs, or the org, and because the targets are inside the org there is no invitation to accept, so the member account sees it immediately. That no-invitation behavior is the headline RAM fact for in-org sharing.

**The decision drill.**
Launching EC2 into a shared VPC subnet is RAM, the shared-VPC pattern, because a cross-account role grants API access but does not give them a place to launch. Granting an analytics role read on one bucket and its KMS key is a resource-based policy, and cross-account it needs both the resource policy and the caller's identity policy to allow it. Letting dev teams self-deploy approved compliant stacks without the permissions to build them freehand is Service Catalog with a launch constraint.

**Service Catalog pieces.**
A product is a versioned template, a portfolio is a shared collection of products with constraints, a launch constraint is the role Service Catalog assumes to provision so the user needs no underlying permissions, and a template constraint limits parameter choices so the approved product cannot be bent out of compliance. The launch constraint is the whole point.

**Firewall Manager.**
Firewall Manager defines a protection once and applies it to every in-scope account, automatically protecting new resources and new accounts as they appear, with optional auto-remediation, which is the one thing only it does.

| Prerequisite | Why |
|---|---|
| Organizations with all features | org-wide scope |
| FMS admin account (auto-registered delegated admin) | central administration, not the management account |
| Config on every member account | FMS detects and evaluates resources through Config |
| RAM enabled | only for the Network Firewall and DNS Firewall policy types (shared configs) |

## The subtle one: RAM sharing, the two-sided handshake, the launch constraint, and the orchestrator role

Several tested edges here.

**RAM org sharing skips invitations, external accounts do not.** In-org targets get access with no accept step, but an account outside your org must accept the resource share invitation, so "the partner still cannot see the shared subnet" is usually an unaccepted external invitation. And RAM shares the resource, not API actions on data, so a data resource like a bucket is a resource-based policy, not RAM.

**Cross-account data access is a two-sided handshake.** A resource-based policy needs the resource to allow the external principal and that principal's identity policy to allow the action, and KMS is the strictest case, where the key policy must enable the other account before its principals can be delegated. This is the same both-sides rule from 4.4 and 5.2.

**The launch constraint is the entire security value of Service Catalog.** Without it, launching a product needs the full permissions to build everything in the template, which defeats governed self-service, and with it users deploy the approved thing while holding almost no standing permissions. Keep the three verbs straight: users pull with Service Catalog, an admin pushes with StackSets, the org grows with Account Factory.

**Firewall Manager is the orchestrator, not the firewall.** WAF is the web ACL, Shield is the DDoS protection, Network Firewall is the VPC firewall, and Firewall Manager is the org-wide layer that deploys and continuously enforces them and auto-applies them to new resources. Protecting one app's ALB is plain WAF, ensuring every ALB across all accounts including future ones carries the rule set is Firewall Manager. Config is the silent prerequisite, so a blank compliance status usually means Config is not enabled in those member accounts, and best practice is to run a new policy without auto-remediation first, then enable it once you trust the dashboard.

## Exam relevance

- **Decide by what you share and to whom:** RAM for infrastructure resources (subnets, transit gateways) to accounts or OUs, a resource-based policy for one data resource to a specific principal, Service Catalog for governed self-service products, Firewall Manager for org-wide network enforcement.
- **RAM in-org sharing skips invitations, external accounts must accept**, and RAM shares the resource, not data-API access.
- **Cross-account data access is two-sided:** the resource policy plus the caller's identity policy, and KMS needs the key policy to enable the other account first.
- **Service Catalog's launch constraint lets users deploy approved products without the underlying permissions**, the keyword answer to governed self-service.
- **Service Catalog (users pull), StackSets (admin pushes), Account Factory (org grows)** are three different verbs.
- **Firewall Manager prerequisites:** Organizations all features, an FMS admin account (delegated admin), Config on every member account, and RAM for the Network Firewall and DNS Firewall policy types.
- **Firewall Manager is the orchestrator that deploys and enforces WAF, Shield, Network Firewall, and DNS Firewall org-wide and auto-applies to new resources.** The actual protection is the underlying service, and Config is the silent prerequisite behind a blank compliance dashboard.
