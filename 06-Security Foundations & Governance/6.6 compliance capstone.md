# 6.6 — Compliance Capstone

**Domain 6: Security Foundations and Governance (14%)**
**Companion to:** `scs-c03-lab-6_6-compliance-capstone.md` (the runnable lab). This file records what was built and *why each result happens*, one level deeper than the lab's terse `Result:` lines.

**Cost:** about $0 if you tear down. Config bills a small amount per configuration item and per rule evaluation, so keep it brief. Artifact and the Well-Architected Tool are free, and Audit Manager is scenario only because it bills.

---

## What I built

- Added a **Config rule** requiring S3 encryption, created a noncompliant bucket, watched it flag, and **auto-remediated** it with an SSM document under a remediation role, flipping it to compliant.
- Enabled **Security Hub** and confirmed it runs its standards on Config rules, separating findings-and-standards from config-compliance-and-remediation.
- Split **Audit Manager** (your evidence) from **Artifact** (AWS's reports) along the shared responsibility line, and pulled a free Artifact report.
- Ran a **Well-Architected** review and read its risk output.

The point was that five services share one job, is what we built compliant and can we prove it, and the whole skill is the lines between them. Two splits are the exam favorites: Config versus Security Hub, and Audit Manager versus Artifact.

---

## The model this proves

Five compliance services each answer a different question, and the exam decides between them on which question is being asked.

| Service | Answers | Mechanism | Free? |
|---|---|---|---|
| AWS Config | is this resource compliant, and can you fix it? | Config rules plus SSM remediation | bills small |
| Security Hub | what are my prioritized findings and standard scores? | aggregates findings, runs standards on Config rules | bills |
| Audit Manager | can I produce evidence for an audit against a framework? | frameworks to controls to auto-collected evidence | bills |
| Artifact | where are AWS's own SOC/PCI/ISO reports? | self-service download portal | free |
| Well-Architected Tool | is this workload's architecture sound? | pillar questionnaire to risk items | free |

Two splits carry most of the weight. **Config versus Security Hub:** Config is the configuration compliance and remediation engine that evaluates and fixes individual resources, and Security Hub is the findings aggregator and standards scorer that sits on top and runs most of its controls as Config rules, so it depends on Config rather than replacing it. **Audit Manager versus Artifact:** Audit Manager collects your evidence about your usage against a framework (customer side), and Artifact hands you AWS's own compliance reports about its infrastructure (provider side), so they sit on opposite sides of the shared responsibility line.

And detect, remediate, and notify are three separate wires.

## What each demo proved

**Config: detect and auto-remediate.**
A managed rule requiring S3 encryption flags a new unencrypted bucket as NON_COMPLIANT, and an automatic remediation with an AWS-managed SSM document applies encryption and flips it to COMPLIANT. The remediation runs under an `AutomationAssumeRole`, not your caller identity, so if that role is missing or lacks `s3:PutEncryptionConfiguration` the fix silently fails and the resource stays noncompliant. This is the 1.4 remediation split restated: the rule detects, a separate role fixes.

**Conformance packs and aggregators.**
A conformance pack bundles rules and remediations as one deployable unit you push org-wide from a delegated admin, while a Config aggregator rolls compliance data from many accounts into one read-only view. The aggregator aggregates, it does not enforce, so you push rules with conformance packs and see them with the aggregator.

**Security Hub: aggregate and score, on top of Config.**
Security Hub runs standards (FSBP as the recommended baseline, plus CIS, PCI, and NIST) whose controls are mostly Config rules, aggregates findings from GuardDuty, Inspector, Macie, and IAM Access Analyzer into ASFF, and scores posture. If Config is off, its control findings do not generate. This is the cleanest split in the domain: Security Hub depends on Config.

**Audit Manager versus Artifact.**
Artifact is the free, read-only portal for AWS's own SOC, PCI, and ISO reports and agreements, proving the provider's infrastructure is certified. Audit Manager continuously collects your evidence, mapping your usage to a framework's controls by auto-pulling from Config, Security Hub, and CloudTrail, and produces an assessment report. Artifact is about AWS, Audit Manager is about you.

**Well-Architected Tool: review the design.**
A Well-Architected review answers a pillar questionnaire (the Security pillar for SCS) and produces high and medium risk items plus an improvement plan. It reviews architecture and decisions, it does not scan live resources like Config or aggregate findings like Security Hub.

## The subtle one: the two splits, the remediation role, and what each tool does not do

Several tested edges here.

**Config versus Security Hub is the cleanest split in the domain.** Config evaluates and fixes individual resources, Security Hub aggregates findings and scores standards on top and depends on Config, since most of its controls are Config rules. "Automatically fix noncompliant resources" is Config remediation, and "a prioritized cross-service, cross-account posture view with standard scores" is Security Hub. Turn Config off and Security Hub's control findings stop.

**Audit Manager versus Artifact falls on the shared responsibility line.** Artifact is AWS's own reports about the provider (its data centers, its certifications), and Audit Manager is continuously collected evidence about your environment against a framework. Provider side is Artifact, customer side is Audit Manager.

**Remediation runs under its own role.** The SSM document uses the `AutomationAssumeRole`, so a missing or under-permissioned role means the rule flags but nothing fixes, the 1.4 two-permission-surface trap again.

**Detect, remediate, and notify are three wires.** Config does not page anyone, so notifications route Config compliance-change events through EventBridge to SNS, the Domain 1 detective pattern.

**The aggregator only shows, and Well-Architected only reviews design.** A Config aggregator gives read-only rollup visibility, not enforcement, and the Well-Architected Tool evaluates architecture, not live resources.

## Exam relevance

- **Five services, five questions:** Config (is a resource compliant and can you fix it), Security Hub (prioritized findings and standard scores), Audit Manager (evidence for an audit against a framework), Artifact (AWS's own compliance reports), Well-Architected Tool (is the workload's architecture sound).
- **Config versus Security Hub:** Config fixes resources, Security Hub scores posture on top and depends on Config. Config off means Security Hub control findings stop.
- **Audit Manager versus Artifact:** your evidence (customer side) versus AWS's reports (provider side), on opposite sides of shared responsibility. Artifact is free.
- **Config remediation runs under an `AutomationAssumeRole`**, and a missing or under-permissioned role is why the rule flags but nothing fixes.
- **Detect, remediate, and notify are separate**, and notifications go through EventBridge to SNS.
- **Conformance packs deploy rules and remediations org-wide, a Config aggregator is read-only rollup visibility, not enforcement.**
- **FSBP is the recommended Security Hub baseline**, and most of its controls are Config rules.
- **The Well-Architected Tool reviews architecture and produces risk items and an improvement plan.** It does not scan live resources or aggregate findings.
