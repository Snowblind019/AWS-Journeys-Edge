# 1.6 — Security Lake

**Domain 1: Detection (16%)**
**Companion to:** `scs-c03-lab-1_6-security-lake.md` (the runnable lab). This file records what was built and *why each result happens*, one level deeper than the lab's terse `Result:` lines.

**Cost:** about $0 for a short lab if you keep it small. Security Lake bills on ingestion and storage, Athena per data scanned, and OpenSearch by the hour, so add one source, partition your queries, and delete the lake and any OpenSearch integration promptly.

---

## What I built

- Enabled **Security Lake** with encryption and lifecycle rules, added VPC Flow Logs as a source, and saw the two subscriber models (query access versus data access).
- Queried the normalized **OCSF tables with Athena**, partitioning on time to keep the scan small.
- Noted the **OpenSearch zero-ETL** integration for frequent low-latency hunting, then deliberately picked the wrong tool for a one-off versus a continuous-dashboard scenario to feel where each wins.
- Placed Security Lake against the simpler **org-trail-to-a-logging-account** pattern, and pinned down **OCSF versus ASFF**.

The point was that Security Lake normalizes many security sources into one OCSF schema in S3, and the subdomain is mostly right-tool decisions: query access versus data access, Athena versus OpenSearch by frequency and latency, and Security Lake versus a plain org trail by whether you actually need multi-source normalization.

---

## The model this proves

Security Lake centralizes and normalizes security data from many sources into the OCSF schema, stored as Parquet in S3 and exposed through Lake Formation tables. The decisions around it are what the exam tests.

| Subscriber type | How it consumes | Reach for when |
|---|---|---|
| Query access | SQL against the Lake Formation tables (Athena, OpenSearch, Redshift) | "let our SIEM query the normalized data" |
| Data access | SQS notification as Parquet lands, read with own code | "run a Lambda on every new event object" |

| | Athena | OpenSearch |
|---|---|---|
| Model | serverless, per data scanned | running cluster |
| Best for | one-off, occasional queries | frequent, low-latency dashboards, full-text |
| The trap | scanning the whole lake unpartitioned | standing up a cluster for a single question |

Security Lake is not always the answer. If you only need to centralize CloudTrail and query occasionally, a plain org trail to a logging account plus Athena is right-sized, and Security Lake earns its keep only when normalizing many sources for many consumers.

| Schema | What it is | Used by |
|---|---|---|
| OCSF | open, multi-vendor schema | Security Lake normalizes to it, the new Security Hub emits it |
| ASFF | AWS finding format | Security Hub CSPM, and ASFF automation does not consume OCSF |

## What each demo proved

**Enable Security Lake and pick sources.**
Creating the data lake with encryption and lifecycle rules and adding VPC Flow Logs normalizes that source into OCSF Parquet. Subscribers then consume in one of two modes: query access runs SQL against the Lake Formation tables, and data access gets an SQS notification as each Parquet object lands and reads it with its own code.

**Athena over the OCSF tables.**
An Athena query against the normalized CloudTrail table answers cross-org questions in SQL, and the discipline is to filter on `time_dt` or `eventDay` so you scan a slice rather than the whole lake, because Athena bills by data scanned and unpartitioned scans are the classic cost blowup.

**OpenSearch zero-ETL: when Athena is not enough.**
For frequent low-latency hunting and dashboards, the OpenSearch zero-ETL integration gives fast repeated queries and optional indexed views for hot subsets, without duplicating the whole lake.

**The tool-choice break.**
For a one-off "did this IP touch any API in 30 days," standing up an OpenSearch cluster is wrong, since you pay for a running cluster and pipeline for a single question, and a partitioned Athena query is right, serverless and pennies. Flip to continuous SOC dashboards queried hundreds of times a day with sub-second drill-downs, and Athena is wrong because each refresh re-scans S3, while OpenSearch is right because a running cluster is exactly what frequent low-latency querying is for. The choice is a function of frequency and latency, not of one tool being better.

**Centralized logging: right-sizing.**
Two patterns. An org CloudTrail trail to a central S3 bucket in a dedicated logging account plus Athena is the simplest and cheapest for keeping an immutable copy and querying occasionally, the bread-and-butter answer. Security Lake with a delegated admin and a rollup Region wins when you need multi-source normalization and cross-region consolidation with subscribers consuming one schema.

## The subtle one: the right-tool decisions, and OCSF versus ASFF

Several decisions carry the exam weight here.

**Query access versus data access.** Query access is SQL against the tables for a SIEM or analyst, and data access is an SQS notification per new object for code to process. "Let our SIEM query the normalized data" is query access, and "run a Lambda on every new event object" is data access.

**Athena versus OpenSearch by frequency and latency.** One-off or occasional is Athena, serverless and cheap when partitioned on time. Frequent, low-latency, dashboard and full-text is OpenSearch, worth the standing cluster. Neither is better in the abstract.

**Security Lake versus a plain org trail.** If the requirement is only to centralize CloudTrail and query occasionally, Security Lake is over-engineered and an org trail to a logging account plus Athena is right-sized. Security Lake earns its keep normalizing many sources for many consumers.

**OCSF versus ASFF.** OCSF is the open multi-vendor schema that Security Lake normalizes to and the new Security Hub emits, for correlating across heterogeneous sources. ASFF is AWS's finding format used by Security Hub CSPM, and ASFF-built automation does not consume OCSF, which is the 1.3 trap. "Normalize many log or finding types into one industry-standard schema for a data lake" is OCSF and Security Lake, and "Security Hub CSPM standards and findings" is ASFF.

---

## Exam relevance

- **Security Lake normalizes many sources into OCSF Parquet in S3**, queryable via Lake Formation tables.
- **Query access subscribers run SQL, data access subscribers get SQS notifications** and read the objects with their own code.
- **Athena is for one-off or occasional queries, partitioned on time to control cost. OpenSearch is for frequent low-latency dashboards and full-text.** Choose by frequency and latency.
- **A plain org trail to a logging account plus Athena is right-sized** for "centralize CloudTrail and query occasionally." Security Lake is for multi-source normalization and many consumers.
- **OCSF is the open multi-vendor schema** (Security Lake, the new Security Hub), and **ASFF is AWS's finding format** (Security Hub CSPM), which does not consume OCSF.
