## The model this proves

Security Hub is the single pane that aggregates and normalizes findings (from GuardDuty, Inspector, Macie, Config, and your own tools) and runs CSPM controls against standards. Its core dependency and its tested distinctions:

- **CSPM controls depend on AWS Config.** The controls evaluate configuration data that Config records, so without Config recording (or not recording a resource type), those controls report `NOT_AVAILABLE` and the score is meaningless. Nothing is broken in Security Hub, it simply has no data.
- **Standards drive the score.** FSBP is AWS's own baseline and the broadest, enabled by default, CIS is the industry baseline, and PCI DSS and NIST are compliance-framework specific, enabled when in scope.
- **ASFF is the ingest format.** Any external tool's findings become first-class Security Hub findings via `BatchImportFindings` in valid ASFF.
- **Central configuration** pushes standards and controls org-wide from the delegated admin.

| Action | Checking | Charged | Finding kept | Use when |
|---|---|---|---|---|
| Disable a control | stops | stops | n/a | the control is irrelevant (service unused) |
| Suppress (automation rule) | continues | continues | yes, marked `SUPPRESSED` | the control is relevant but a specific finding is acceptable noise |

| Mechanism | Where it acts | Does what | Example |
|---|---|---|---|
| Automation rule | inside Security Hub, on the finding | relabel severity or workflow, suppress, add note | auto-raise severity on prod-tagged resources |
| EventBridge | outside Security Hub | Lambda remediation, SSM runbook, SNS page, ticket | quarantine the instance, open a Jira ticket |

## What each demo proved

**The Config dependency, broken first.**
Enabling Security Hub with default standards while Config is not recording leaves a chunk of controls at `NOT_AVAILABLE`, so the score means nothing. This is the most instructive failure in the lab: Security Hub is not broken, it simply has no configuration data to evaluate. Any "our score looks wrong" or "controls show no data" scenario is a Config-recording problem first.

**The fix: turn on the Config recorder.**
Starting the Config recorder for all supported types (with global resource types) flips `NOT_AVAILABLE` to `PASSED` or `FAILED` as the data arrives. This is the preview of 1.4, and it makes the CSPM dependency concrete.

**Standards and the score.**
FSBP is the default broad baseline, CIS is the industry benchmark, and PCI and NIST are enabled only when in scope. The score is only as meaningful as the underlying Config data and the standards you have chosen.

**Cross-region aggregation.**
A finding aggregator with region linking gives one home Region a single view across all linked Regions, so analysts stop hopping region to region. But you still enable Security Hub in every region, because a region where it is off produces nothing to aggregate, the same regional-blind-spot logic as GuardDuty.

**Automation rules: no-code finding handling.**
Automation rules update finding fields (severity, workflow status, note) or suppress the moment a finding arrives, with no Lambda, which is how you auto-raise severity on prod-tagged resources or auto-suppress a benign control on a sandbox account.

**ASFF ingest.**
`BatchImportFindings` brings a custom scanner, CI/CD gate, or homegrown tool into Security Hub as first-class findings, as long as the finding is valid ASFF. This is how everything lands in one pane and one automation path.

**Org-wide central configuration.**
Delegating Security Hub to a security account and using central configuration lets the delegated admin define one policy (which standards, which controls, aggregation) and apply it across all accounts and regions, instead of configuring each one.

## The subtle one: disable vs suppress, and automation rules vs EventBridge

Two clean distinctions the exam tests directly, sitting on top of the Config dependency.

**Disable versus suppress.** Disabling a control stops the check and stops the charge, and is right when the control is irrelevant because you do not use that service. Suppressing, via an automation rule, keeps checking but mutes the finding, which stays for audit with a `SUPPRESSED` workflow status, and is right when the control is relevant but a specific finding is acceptable noise. Disable equals do not check and do not pay, suppress equals check but mute.

**Automation rules versus EventBridge.** Automation rules act inside Security Hub on the finding record, relabeling or suppressing. EventBridge acts outside, driving Lambda remediation, an SSM runbook, an SNS page, or a ticket. "Change the finding's severity automatically" is an automation rule, and "quarantine the instance or open a Jira ticket" is EventBridge.

Underneath both, the Config dependency: a wrong-looking score is a Config-recording issue first, not a Security Hub misconfiguration.

## Exam relevance

- **Security Hub CSPM controls depend on AWS Config recording.** `NOT_AVAILABLE` controls or a wrong-looking score is a Config-recording problem, not a Security Hub one.
- **FSBP is the default broad baseline**, CIS is the industry benchmark, and PCI and NIST are enabled when in scope.
- **Disable a control to stop checking and stop paying** (irrelevant service). **Suppress via an automation rule to keep checking but mute** an acceptable finding, which is kept for audit as `SUPPRESSED`.
- **A finding aggregator gives a single cross-region view**, but Security Hub must still be enabled in every region.
- **Automation rules act inside Security Hub** (relabel, suppress). **EventBridge acts outside** (remediate, page, ticket).
- **`BatchImportFindings` in ASFF ingests external tools' findings** into the same pane and automation.
- **Central configuration enforces the same standards and controls across many accounts and regions** from the delegated admin, without per-account setup.
