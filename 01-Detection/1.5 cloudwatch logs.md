## What I built

- **Wired CloudTrail into CloudWatch Logs** with a role, since that is a separate delivery path from the S3 copy and nothing can watch the logs without it.
- Built the **proactive pipeline**: a metric filter for root-account usage feeding an alarm to SNS, the CIS monitoring control in a few API calls.
- Contrasted it with **Logs Insights** (investigate after the fact) and a **subscription filter** (ship matching events in near real time).
- Applied a **data protection policy** that masks credit card and SSN data at ingest, with audit findings alongside.

The point was that CloudWatch Logs is the log pipeline, and the subdomain is really three decisions: notify versus investigate, count versus forward, and detect versus mask, plus the wiring prerequisite that trips people first.

---

## The model this proves

CloudWatch Logs ingests log events, and you act on them three ways, each a distinct exam answer. Underneath, CloudTrail to CloudWatch Logs is a separate delivery path from the S3 copy, wired with a role, and without it there is nothing to watch.

| Mechanism | Mode | Does what | Reach for when |
|---|---|---|---|
| Metric filter plus alarm | push, notify | counts matches into a metric you alarm on | "tell me when the count crosses a threshold" |
| Logs Insights | pull, investigate | query over historical logs | "find or discover what happened" after the fact |
| Subscription filter | push, forward | ships matching events in near real time to Lambda, Kinesis, Firehose, or OpenSearch | "centralize into a SIEM" or "process events as they arrive" |

The net-new piece is data protection, which masks sensitive data at ingest, before it is stored:

| Operation | Effect | Metric |
|---|---|---|
| Audit | detects and reports findings, log unchanged | `LogEventsWithFindings` (namespace `AWS/Logs`, free) |
| De-identify (mask) | masks the value before storage | n/a |

## What each demo proved

**Wiring CloudTrail into CloudWatch Logs: the prerequisite.**
CloudTrail to CloudWatch Logs is not automatic. You create the log group and give CloudTrail a role to write to it, and the S3 copy and the CloudWatch Logs copy are separate delivery paths. "We have a trail but no alarms ever fire" is usually a trail never integrated with CloudWatch Logs, or the wrong role.

**Metric filter plus alarm: the notify pipeline.**
A metric filter matching root-account usage feeds a metric, and an alarm on that metric pages SNS. Signing in as root fires the alarm, which is the CIS monitoring control in three API calls. A metric filter only counts events from the moment it exists forward, so it never alerts on something that happened before it was created.

**Logs Insights: investigate after the fact.**
The same root login is found instantly with a Logs Insights query, but only because you went looking, and it notified no one. Insights is pull and investigate, the alarm is push and notify. Pick based on whether the question wants discovery or notification.

**Subscription filter: ship the events.**
A subscription filter ships the actual matching events in near real time to Lambda, Kinesis, Firehose, or OpenSearch, rather than counting them. "Centralize all accounts' logs into one logging account or SIEM," or "process matching events with Lambda as they arrive," is a subscription filter, while "tell me when the count crosses a threshold" is a metric filter plus alarm.

**Data protection policy: mask at ingest.**
A data protection policy masks credit card and SSN data as it is ingested, before it is stored, so a logged card number appears as asterisks everywhere downstream. It has two operations: Audit detects and reports findings without changing the log, and De-identify actually masks. You usually want both, detect and protect.

## The subtle one: the three-way filter split, and masking mechanics

Two clusters of distinction carry the exam weight here.

**The filter split.** A metric filter turns matches into a count you alarm on (notify). Logs Insights queries history to discover (investigate). A subscription filter forwards the matching events themselves in near real time (centralize or process). Notify versus investigate versus forward is the whole decision, and a metric filter only sees events forward from its creation, which is why historical questions go to Logs Insights.

**Masking mechanics.** Data protection masks at ingest, before storage, so the raw value is never written, and the masked value is what Logs Insights, metric filters, subscription filters, and the `GetLogEvents` and `FilterLogEvents` APIs all see. Only an identity with the `logs:Unmask` permission can reveal the raw value, which is the answer to letting logs flow to a SIEM without ever exposing card numbers. The `LogEventsWithFindings` metric (namespace `AWS/Logs`, free) is what you alarm on to know which app is leaking PII. An account-level policy covers all existing and future log groups while a log-group-level policy is one per group, and they combine, so "enforce masking everywhere including log groups created next month" is the account-level policy. This is masking in transit before storage, which is different from Macie scanning data at rest in S3, so PII in logs at ingest is CloudWatch data protection and sensitive data sitting in S3 is Macie.

## Exam relevance

- **CloudTrail to CloudWatch Logs is a separate delivery path from S3** and must be wired with a role. "Trail exists but no alarms fire" is a missing or wrong CloudWatch Logs integration.
- **Metric filter plus alarm notifies on a count and only counts forward from creation.** Logs Insights investigates history but does not notify. Choose by discovery versus notification.
- **A subscription filter forwards matching events in near real time** to Lambda, Kinesis, Firehose, or OpenSearch. That is the SIEM-centralization and event-processing answer, versus a metric filter for threshold alarms.
- **A data protection policy masks PII at ingest before storage**, masked at all egress points, revealed only with `logs:Unmask`. Audit detects (the `LogEventsWithFindings` metric), De-identify masks, and you usually want both.
- **Account-level data protection covers all current and future log groups**, log-group-level is per group, and they combine.
- **Masking is in transit before storage (CloudWatch data protection)**, which is different from Macie scanning data at rest in S3.
