# 1.1 — CloudTrail

**Domain 1: Detection (16%)**
**Companion to:** `scs-c03-lab-1_1-cloudtrail.md` (the runnable lab). This file records what was built and *why each result happens*, one level deeper than the lab's terse `Result:` lines.

**Cost:** about $0 for a short lab. Management events and the first trail copy are free, storage is pennies, and the only real charge is data events, which bill per event, so keep the selector scope small.

---

## What I built

- A logging bucket with the **exact policy CloudTrail requires**: an ACL-check grant and a write grant scoped to `AWSLogs/account`, with the `bucket-owner-full-control` ACL condition and the `aws:SourceArn` confused-deputy guard.
- A **multi-region trail with log file validation** enabled, the two settings that matter, then started logging.
- Proved **data events are off by default** (management events appeared, S3 object access did not), added an advanced event selector to capture S3 data events, and confirmed they then appeared.
- Ran `validate-logs` to prove integrity, then deleted a log object and re-ran it to watch the digest chain flag the tamper.

The point was that CloudTrail is the audit backbone, and its defaults are traps. It cannot deliver without the right bucket policy, it misses global events unless multi-region, it omits data events unless you opt in, and it cannot prove integrity unless validation was on from the start.

---

## The model this proves

CloudTrail records API activity, and three things have to be right or the audit is silently incomplete.

- **Delivery.** CloudTrail cannot write to a bucket without an explicit grant, so the bucket policy is a hard prerequisite. It needs an ACL-check statement (`s3:GetBucketAcl` on the bucket) and a write statement (`s3:PutObject` on `AWSLogs/account/*`), both with the `aws:SourceArn` condition that guards against the confused deputy, and the write statement with the `s3:x-amz-acl` `bucket-owner-full-control` condition.
- **Scope.** Management events are on by default, data events are opt-in, and global-service events log only in us-east-1.
- **Integrity.** Log file validation produces hash-chained, signed digest files, but it is off by default and must be enabled at creation.

| Event type | On by default | Volume | Examples |
|---|---|---|---|
| Management | yes | low | control-plane calls (bucket policy change, `RunInstances`) |
| Data | no, opt-in | high | S3 `GetObject`/`PutObject`, Lambda `Invoke` |
| Insights | no, opt-in | derived | unusual call-rate or error-rate patterns |

## What each demo proved

**The bucket policy: delivery prerequisite.**
CloudTrail cannot write without the grant, so a missing or mis-scoped policy is why a trail "fails to create" or "stops delivering." The ACL-check plus write statements, scoped to `AWSLogs/account`, are the minimum, and both carry the `aws:SourceArn` confused-deputy guard.

**Trail creation: the two settings that matter.**
Multi-region and log file validation are the two you must set. Multi-region is why global events get captured, and validation is what makes integrity provable later. Both default the wrong way for security.

**Data events off by default.**
Doing S3 object activity, the management event (the bucket policy change) lands in the trail while the object-level `GetObject` and `PutObject` do not, because data events are opt-in. This is the single most common "missing logs" scenario.

**Advanced event selector: capture data events.**
Adding a selector for `eventCategory` Data and `resources.type` `AWS::S3::Object` makes the object-level events appear. Because data events are high-volume and billed per event, you scope selectors tightly (specific buckets, read-only versus write-only) rather than "all data events," or the bill and the noise both explode.

**`validate-logs`: prove integrity.**
Running `validate-logs` walks the digest files, each of which hash-chains to the previous and is signed with a CloudTrail private key, and confirms no log file was modified or deleted. This is how you testify after a breach that the logs are trustworthy.

**Tamper detection: prove it catches deletion.**
Deleting a single delivered log object and re-running `validate-logs` reports the file as missing and the digest chain as broken. An attacker who deletes evidence cannot do so silently.

## The subtle one: the defaults that fail silently, and the cross-account ACL trap

This subdomain is a set of defaults that betray you, plus one cross-account trap.

**The `bucket-owner-full-control` ACL condition** is what lets a logging account own objects delivered by a different account's trail. Drop it and cross-account delivery breaks while same-account quietly still works, which is the "works in test, fails in prod" trap. The `aws:SourceArn` condition is the confused-deputy guard, and without it any trail could target your bucket.

**The global-events trap:** IAM, STS, CloudFront, and Route 53 log only in us-east-1, so a single-region trail elsewhere misses every IAM and STS event, exactly the events you want during an incident. "We are not seeing IAM activity in our trail" is almost always a single-region trail, and `--is-multi-region-trail` is the fix.

**Data events are opt-in and validation is off by default.** Object-level access is invisible until you add a selector, and you cannot prove integrity unless validation was enabled from the start. An incident is the wrong time to discover either gap.

**Detection is not prevention.** Validation tells you evidence was tampered with, but to stop deletion at all you add S3 Object Lock (the 5.8 WORM control) and a separate logging account. The layered answer is detection plus prevention, not one or the other.

---

## Exam relevance

- **CloudTrail needs a bucket policy** with an ACL-check and a write grant scoped to `AWSLogs/account`, plus `aws:SourceArn` and, for cross-account, the `bucket-owner-full-control` ACL condition. A missing or mis-scoped policy is why a trail fails to create or stops delivering.
- **Global services (IAM, STS, CloudFront, Route 53) log in us-east-1**, so use a multi-region trail. Missing IAM activity means a single-region trail.
- **Management events are on by default, data events are opt-in and high-volume**, so scope selectors tightly.
- **Enable log file validation at creation.** It produces hash-chained signed digests, and `validate-logs` is how you prove no log was modified or deleted.
- **Detection (validation) plus prevention (Object Lock, a separate logging account)** is the layered, exam-preferred answer for tamper-proof logs.
