## The model this proves

GuardDuty is managed threat detection, and its defining properties are each a tested point.

- **Independent of your log configuration.** It consumes CloudTrail, VPC Flow Logs, DNS logs, and runtime signals at the service level, so you do not enable those inputs for it. Enabling the detector is the whole setup.
- **Regional.** A detector sees only its own region, so the best-practice answer is to enable it in every region including unused ones, because attackers deliberately operate in regions you ignore.
- **Structured findings.** The naming scheme is `ThreatPurpose:ResourceType/ThreatFamily.Mechanism!Artifact`, which you parse rather than memorize (the mechanism suffix like `!DNS` or `!Tor` tells you how it was detected).

The real discriminator work is the service-confusion axis, which the exam leans on hardest:

| Service | Question it answers | Data it uses |
|---|---|---|
| GuardDuty | is something malicious happening? | logs and behavior (CloudTrail, flow, DNS, runtime) |
| Macie | where is my sensitive data? | S3 object contents (ML classification) |
| Inspector | what is vulnerable? (CVEs, reachability) | EC2/ECR/Lambda software inventory |
| Config | is this configured to policy? | resource configuration history |
| Detective | how did this unfold? | GuardDuty, CloudTrail, and VPC graph, post-finding |

## What each demo proved

**Enable the detector: detection with nothing else on.**
`create-detector --enable` turns on foundational detection and Extended Threat Detection immediately, with no log sources configured. GuardDuty is regional, so the same enablement has to happen in every region, including unused ones, or those regions are blind spots.

**Sample findings: the independence proof.**
With no VPC Flow Logs and no trail, `create-sample-findings` still produces findings, which is the concrete proof that GuardDuty never needed you to turn on its inputs. The finding names parse left to right into threat purpose, resource, and detection mechanism.

**Trusted versus threat lists: the invertible trap.**
A trusted IP list suppresses findings for those IPs (your scanner, VPN egress, CI runners), and a threat IP list generates findings for traffic to or from those IPs (your own known-bad IOCs). Swap the contents and you either go blind to a real attacker or drown in alerts about your own scanner. There is one trusted list per detector but multiple threat lists, and GuardDuty already ships AWS and third-party feeds (Proofpoint, CrowdStrike) for free, so custom threat lists are additive.

**Suppression rules: quiet without losing data.**
A suppression rule is a saved filter with auto-archive. Matching findings are archived out of the default console view but still exported to S3 and EventBridge, so the audit trail stays intact. Suppression archives, it does not delete, which is exactly the answer when a question asks to cut console noise without losing records for compliance. Disabling the finding type or the protection plan would actually lose data.

**Org-wide: delegated admin and auto-enable.**
Delegating GuardDuty to a dedicated security account (not the management account) and setting auto-enable to ALL means every current and future member account is covered, which is the answer to guaranteeing no new account is a blind spot.

**EventBridge: the response seam.**
Findings land on EventBridge with source `aws.guardduty`, and from there they fan out to SNS to notify, Lambda to remediate, or Security Hub to aggregate. You react to the event rather than polling GuardDuty, which is the seam into the Incident Response domain.

## The subtle one: the invertible list, suppression semantics, and regional blind spots

Three tested subtleties here.

**Trusted equals suppress, threat equals alert, and the lists are invertible in the worst way.** Putting bad IPs in the trusted list blinds you, and putting your scanner in the threat list buries you. The one-trusted-list-per-account limit is a tested detail, while threat lists can be many.

**Suppression archives, it does not delete.** Suppressed findings still flow to Security Hub exports and S3, so suppression is the "reduce noise but keep the records" answer, whereas disabling a finding type or protection plan loses data.

**GuardDuty is regional**, so a single-region enablement is a blind spot by design, and attackers exploit exactly the regions you do not watch. Enable everywhere, and use org auto-enable so new accounts are never gaps.

## Exam relevance

- **GuardDuty answers "is something malicious happening"** and consumes CloudTrail, flow, DNS, and runtime independently of whether you enabled those logs. Enabling the detector is all it needs.
- **It is regional.** Enable in every region including unused ones, and use delegated admin with auto-enable ALL so no account is a blind spot.
- **Trusted IP list suppresses, threat IP list alerts.** One trusted list per account, multiple threat lists, and AWS and third-party feeds are built in and free.
- **Suppression rules archive findings out of the console but keep exporting** to S3 and Security Hub. That is the "cut noise without losing compliance records" answer, while disabling the finding type or plan loses data.
- **Findings publish to EventBridge (source `aws.guardduty`)** for SNS, Lambda, or Security Hub. React to the event, do not poll.
- **Service confusion is the real battleground:** malicious behavior is GuardDuty, sensitive-data location is Macie, CVEs and reachability are Inspector, config drift is Config, and post-finding investigation is Detective.
