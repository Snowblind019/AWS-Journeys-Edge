# 1.7 — Service Logging Failure Modes & Macie

**Domain 1: Detection (16%)**
**Companion to:** `scs-c03-lab-1_7-logging-macie.md` (the runnable lab). This file records what was worked through and *why each result happens*, one level deeper than the lab's terse lines.

**Cost:** about $0 if you keep Macie minimal and disable it after. The logging fixes are free configuration changes, and Macie automated discovery bills per GB while jobs bill per byte, so scope both tightly.

---

## What I built

- Worked through the **service-specific logging failure modes** for API Gateway, Lambda, CloudFront, Route 53, and VPC Flow Logs, fixing each and learning why it goes silent.
- Revisited **Macie** from the Detection angle: enabled it, scoped the sensitivity inspection template, and mapped its two discovery modes, two finding types, and multi-account model.

The point was two things. Every AWS service logs differently and goes silent for its own specific reason, almost always a missing role, a wrong destination, or a wrong Region rather than a broken service, and Macie is the at-rest PII detector that pairs with the 1.5 in-transit masking.

---

## The model this proves

**Part A, logging failures.** Logs going missing is rarely a broken service. It is almost always that the logging resource exists but cannot write, or is pointed at the wrong place. The causes cluster into a few shapes: a missing role, a wrong destination or delivery delay, or a wrong Region or missing resource policy.

| Service | Log types | Usual silent cause |
|---|---|---|
| API Gateway | execution logs, access logs | account-level CloudWatch Logs role not set |
| Lambda | function logs to CloudWatch | execution role lacks `logs:` permissions |
| CloudFront | standard logs, real-time logs | wrong destination, or standard-log delivery delay |
| Route 53 | public query logging, Resolver query logging, health checks | log group in wrong Region, or resource policy missing |
| VPC Flow Logs | to CloudWatch, S3, or Firehose | delivery IAM role or bucket policy missing or wrong |

**Part B, Macie.** Macie answers "where is my PII," which no other detection service does, and it scans data at rest in S3, the counterpart to the 1.5 in-transit log masking.

| Mode | What it does | When |
|---|---|---|
| Automated sensitive data discovery | daily sampling across all buckets, sensitivity scores and a data map | broad, continuous, low-cost visibility |
| Sensitive data discovery jobs | deep exhaustive scan of selected buckets, one-time or scheduled | targeted, thorough analysis |

## Part A: the per-service failures

**API Gateway: the account-level role.**
Two log types. Execution logs are what API Gateway did handling the request (per stage, at ERROR or INFO), and access logs are one custom-format line per request to a log group you specify. The reliably tested failure: you enable execution logging on the stage and nothing appears, because API Gateway also needs an account-level IAM role (set once per Region, trusting `apigateway.amazonaws.com` with `AmazonAPIGatewayPushToCloudWatchLogs`) that is separate from the stage toggle. Both must be present. Execution versus access is also a discriminator: internal processing and integration errors is execution logs, a clean per-request audit line you control is access logs.

**Lambda: logging is an IAM problem.**
A function writes to CloudWatch only if its execution role allows it, via `AWSLambdaBasicExecutionRole` (`logs:CreateLogGroup`, `CreateLogStream`, `PutLogEvents`). "Runs fine but no logs" is the execution role missing `logs:` permissions, not a CloudWatch problem, because invocation permission and logging permission are separate surfaces, the same split as the 1.4 Config remediation role. Advanced logging controls give JSON structured logging, a minimum level, and a custom log group with no code change.

**CloudFront: standard versus real-time.**
Standard logs (v2) are detailed request logs to S3, CloudWatch, or Firehose, comprehensive but delayed. Real-time logs are a configurable sample streamed to Kinesis Data Streams within seconds. The discriminator is latency: investigate after the fact is standard logs, detect and react within seconds is real-time to Kinesis, and picking standard for a real-time requirement is the trap because they arrive too late.

**Route 53: query logging versus health checks.**
Public DNS query logging is queries to a public hosted zone, to CloudWatch, and the log group must be in us-east-1 with a resource policy. Resolver query logging is queries originating inside your VPC, to CloudWatch, S3, or Firehose, the DNS-exfiltration source from 1.6. Health checks are endpoint probing and DNS failover, not logging. "Log DNS queries from inside my VPC" is Resolver query logging, "log queries hitting my public domain" is public hosted zone query logging, and public query logging must use us-east-1 because Route 53 is global and logs through that Region.

**VPC Flow Logs: delivery permissions and a coverage blind spot.**
Flow Logs deliver to CloudWatch (an IAM role they assume), S3 (a bucket policy), or Firehose, and "enabled but the log group stays empty" is that delivery role or bucket policy missing or wrong, since the resource can exist and still write nothing. The coverage blind spot is the other half: Flow Logs do not capture Amazon-provided DNS resolver queries, DHCP, instance metadata at 169.254.169.254, or Windows license activation, so "we don't see DNS lookups in Flow Logs" is by design and the answer is Route 53 Resolver query logging, not a Flow Log fix.

## Part B: Macie

Macie is the sensitive-data detection service, and here it is a monitoring and alerting signal and the at-rest counterpart to 1.5's in-transit masking. Automated discovery samples daily across all buckets for broad cheap visibility, and discovery jobs scan selected buckets exhaustively for depth. It inspects with **managed data identifiers** (built-in ML and pattern matching for PII, financial data, and credentials), **custom data identifiers** (your regex with optional keywords and a proximity rule), and **allow lists** (patterns to ignore). It produces two finding types: **policy findings** (bucket-level security like unencrypted, public, or shared outside the org) and **sensitive data findings** (object-level reports of what was found). Macie is regional with a delegated administrator, members cannot change the identifiers or see each other's findings, and findings route to EventBridge and Security Hub for automated response, such as a Lambda that blocks public access on an offending bucket.

## The subtle one: silent-failure causes, the Flow Logs blind spot, and at-rest versus in-transit

Several tested edges here.

**The logging silent-failure causes are service-specific** and worth memorizing as a set: API Gateway's account-level role, Lambda's execution role, CloudFront's latency and destination, Route 53's us-east-1 requirement and resource policy, and Flow Logs' delivery role or bucket policy. The instinct is "the resource exists but cannot write," not "the service is broken."

**The Flow Logs coverage blind spot.** Flow Logs never capture Amazon DNS resolver queries, DHCP, the metadata endpoint, or Windows activation. Missing DNS in Flow Logs is by design, and the fix is Resolver query logging.

**Macie's breadth versus depth.** Automated discovery samples for broad cheap visibility, jobs scan exhaustively for a specific-bucket audit, and a sensitivity score of 0 does not mean clean, it means not yet analyzed or nothing found in the sample (a score of -1 is excluded, and 1 to 100 is increasing sensitivity).

**At rest versus in transit.** Macie scans PII at rest in S3, and CloudWatch Logs data protection masks PII in transit in logs before storage. Same data type, different location, different service.

## Exam relevance

- **Logs going silent is almost always a permission, destination, or Region problem**, not a broken service. API Gateway needs the account-level CloudWatch Logs role plus the stage toggle, Lambda needs `logs:` permissions on its execution role, Route 53 public query logging needs the log group in us-east-1, and Flow Logs need the delivery role or bucket policy.
- **API Gateway execution logs are internal processing, access logs are the per-request audit line.**
- **CloudFront standard logs are complete but delayed, real-time logs stream a sample to Kinesis within seconds.** Choose by latency.
- **Route 53 Resolver query logging is DNS from inside your VPC, public hosted zone query logging is queries to your public domain.**
- **Flow Logs never capture Amazon DNS resolver, DHCP, metadata, or Windows activation traffic.** Missing DNS is by design, so use Resolver query logging.
- **Macie automated discovery is breadth (sampling, cheap, continuous), discovery jobs are depth (exhaustive, targeted audit).** A score of 0 is not "clean."
- **Macie scans PII at rest in S3, CloudWatch Logs data protection masks PII in transit in logs.** Different location, different service.
