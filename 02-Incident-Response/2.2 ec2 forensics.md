## What I built

- Captured **memory first** from the running instance with SSM Run Command and a memory-acquisition tool, streaming the dump to the forensics account, and hit the isolation-versus-reachability tension from 2.1.
- Acquired the **disk** the right way after building the wrong way first: a default-encrypted snapshot cannot cross accounts, so I re-encrypted under a customer-managed key, shared it, and re-copied under a forensic-account-owned key.
- Mounted the evidence **read-only** on a forensic instance and hashed it, then stored it in a **COMPLIANCE-mode Object Lock** bucket for immutable custody.
- Studied the **Automated Forensics Orchestrator** as the at-scale answer.

The point was that forensic acquisition is an ordered, evidence-preserving pipeline: memory before anything else, disk via a CMK-keyed snapshot that can actually cross accounts, read-only mounting, and WORM retention. The cross-account encrypted-snapshot trap is the highest-frequency exam item in it.

## The model this proves

Forensic acquisition follows a strict order, and each step exists to preserve evidence.

- **Memory first, from the running instance.** RAM does not survive a stop (the 2.1 lesson), so you capture it while the instance runs, via SSM Run Command executing AVML or LiME and streaming the dump to S3 in the forensics account, tagged with OS and kernel so Volatility can parse it.
- **Disk via snapshot, copy, and share, and the encryption matters.**
- **Read-only mount always.** Mounting read-write alters access times, journal state, and metadata, which taints the evidence, so you mount with `-o ro` and hash before and after.
- **Immutable retention.** S3 Object Lock in COMPLIANCE mode means no one, not even root, can delete or overwrite before expiry, which is the forensic answer over the weaker GOVERNANCE mode.

| Snapshot encryption | Cross-account share works? | What is needed |
|---|---|---|
| Unencrypted | yes | just the share permission |
| Default `aws/ebs` (AWS-managed) | no, dead end | re-copy under a CMK first |
| Customer-managed CMK | yes | share the CMK and grant `kms:Decrypt`, `DescribeKey`, `CreateGrant`, `ReEncrypt*` |

When this has to happen at scale or consistently across the org, the Automated Forensics Orchestrator is the deployable, Step Functions-orchestrated answer.

## What each demo proved

**Memory acquisition: first, and from the running instance.**
SSM Run Command executes a memory-acquisition document that streams a RAM dump to S3 in the forensics account, tagged with OS and kernel version for Volatility. This is where 2.1's isolation collides with reachability: a no-egress SG and NACL deny cut the instance off from SSM, so memory capture fails unless you add VPC interface endpoints for `ssm`, `ssmmessages`, and `ec2messages`. That PrivateLink path is the elegant answer, isolated from the internet but still reachable by your forensic tooling. And with no SSM agent or no instance role, there is no capture path at all, which is why acquisition is a preparation task.

**Disk acquisition: the cross-account encryption trap.**
Sharing a snapshot encrypted with the default `aws/ebs` AWS-managed key to the forensics account does not work, because you cannot share an AWS-managed-key snapshot across accounts. The correct path re-encrypts the snapshot under a customer-managed key, shares that key (granting the target account `kms:Decrypt`, `kms:DescribeKey`, `kms:CreateGrant`, and `kms:ReEncrypt*`), then shares the snapshot. Inside the forensics account you re-copy it under a key the forensics account owns, so the evidence survives even if the application account is attacker-controlled or deleted.

**Read-only mount: do not taint the evidence.**
Creating a volume from the forensic-owned snapshot and mounting it `-o ro` on the forensic instance preserves access times, journal state, and metadata, and hashing the image before and after proves integrity. A read-write mount breaks chain of custody.

**Chain of custody and immutable retention.**
An S3 Object Lock bucket in COMPLIANCE mode makes the evidence undeletable and unoverwritable for the retention period, even by root, which GOVERNANCE mode does not guarantee. CloudTrail is the who-did-what audit of the whole acquisition, and tags carry the incident ID and responder.

**Automated Forensics Orchestrator: acquisition at scale.**
The orchestrator is the deployable, serverless, Step Functions solution with five stages: triage, memory acquisition, disk acquisition, investigation, and the forensic AMI and SSM-document builder. A detection lands in Security Hub, EventBridge triggers triage, and the pipeline does everything you just did by hand, including the double CMK copy.

## The subtle one: the CMK cross-account trap, isolation versus reachability, and shared-role blast radius

Several tested edges here.

**The AWS-managed-key cross-account snapshot trap is the highest-frequency item.** A snapshot encrypted with `aws/ebs` cannot be shared across accounts, full stop. You must re-copy under a customer-managed CMK and grant the target account `kms:Decrypt`, `kms:DescribeKey`, `kms:CreateGrant`, and `kms:ReEncrypt*`. Unencrypted snapshots share fine, default-encrypted ones are a dead end. The double copy, re-keying under the forensic account's own CMK, is what makes the evidence independent of the possibly-compromised app account.

**Isolation versus reachability.** The 2.1 no-egress containment cuts SSM off, so memory capture needs PrivateLink interface endpoints for `ssm`, `ssmmessages`, and `ec2messages`. Isolated from the internet, still reachable by forensic tooling, is the answer.

**Read-only or you taint it.** Always mount `-o ro` and hash before and after, because a read-write mount alters metadata and breaks custody. COMPLIANCE-mode Object Lock, not GOVERNANCE, is the immutability answer.

**Shared-role blast radius.** Isolation invalidates all live credential sessions for the compromised instance's role, so other instances sharing that role lose their credentials too and break if they do not refresh. Role design is incident-response design, the same shared-role lesson from 2.1.

## Exam relevance

- **Capture memory first, from the running instance**, via SSM Run Command and AVML or LiME to S3, tagged with OS and kernel. RAM does not survive a stop.
- **No-egress isolation blocks SSM**, so add VPC interface endpoints for `ssm`, `ssmmessages`, and `ec2messages` to capture privately without internet egress.
- **You cannot share a snapshot encrypted with the AWS-managed `aws/ebs` key across accounts.** Re-copy under a customer-managed CMK and grant `kms:Decrypt`, `kms:DescribeKey`, `kms:CreateGrant`, and `kms:ReEncrypt*`. Unencrypted snapshots share fine.
- **Double-copy the evidence under a forensic-account-owned CMK** so it survives the app account being compromised or deleted.
- **Mount evidence read-only (`-o ro`) and hash before and after.** Read-write taints the evidence.
- **Store evidence in a COMPLIANCE-mode Object Lock bucket**, not GOVERNANCE, for undeletable retention.
- **The Automated Forensics Orchestrator is the at-scale, org-wide answer**, and isolation revoking role sessions breaks other instances sharing that role.
