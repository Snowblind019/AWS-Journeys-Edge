# 2.5 — Automated Remediation

**Domain 2: Incident Response (14%)**
**Companion to:** `scs-c03-lab-2_5-automated-remediation.md` (the runnable lab). This file records what was built and *why each result happens*, one level deeper than the lab's terse `Result:` lines.

**Cost:** about $0. EventBridge, Lambda, SSM Automation, and SNS are pay-per-use and trivial here. The real cost of this subdomain is operational risk, since a bad auto-remediation is a self-inflicted outage, so filter `[SAMPLE]` findings and scope by tag or account in every rule.

---

## What I built

- Learned the **three event patterns** that drive remediation: GuardDuty straight to EventBridge, Security Hub Findings - Imported for the fully automatic path, and Security Hub Findings - Custom Action for the human-in-the-loop path.
- Built the **wrong answers first**: auto-remediating everything (a self-inflicted outage), trying to isolate a resource with a Security Hub automation rule (which only edits the finding), and one over-permissioned Lambda with hardcoded credentials.
- Built the **correct pipeline**: a precise EventBridge match, an SSM Automation runbook under a least-privilege role, a close-the-loop step, and a human gate for destructive actions.
- Placed **ASR** as the prebuilt, standards-aligned answer.

The point was that automated remediation is a pipeline with guardrails. EventBridge matches the finding and Lambda or SSM acts on the resource, but the whole discipline is precision and blast-radius control: filter samples, scope tightly, use least-privilege roles, and gate destructive actions behind a human.

---

## The model this proves

Remediation is EventBridge matching a finding and a target acting on the resource, and the exam tests the guardrails around it.

| Event | detail-type | Mode |
|---|---|---|
| GuardDuty finding | `GuardDuty Finding` (source `aws.guardduty`) | direct |
| Security Hub, every finding | `Security Hub Findings - Imported` | fully automatic |
| Security Hub, analyst-clicked | `Security Hub Findings - Custom Action` | human-in-the-loop |

| | Security Hub automation rule | EventBridge rule to Lambda or SSM |
|---|---|---|
| Acts on | the finding record (ASFF fields) | the underlying resource |
| Can do | severity, workflow status, suppress, notes | isolate, encrypt, revoke, snapshot |
| Reach for | relabel or suppress a finding | act on the resource |

The automation-rule-versus-EventBridge line is the high-yield distinction restated from 1.3: an automation rule can only edit ASFF fields, so acting on a resource always needs EventBridge.

| Pipeline step | Action | Guards against |
|---|---|---|
| Match | EventBridge rule on type, Workflow NEW, Sample false | false-positive and sample triggers |
| Act | SSM Automation runbook (prefer) or Lambda, least-privilege role | over-broad remediation surface |
| Close loop | set finding RESOLVED or NOTIFIED, SNS, CloudWatch | re-trigger loops, missing audit |
| Human gate | custom action for destructive steps, optional `aws:approve` | self-inflicted outage on false positives |

ASR (Automated Security Response on AWS) is the named, deployable, multi-account, standards-aligned solution, the remediation cousin of the 2.2 forensics orchestrator.

## What each demo proved

**The three events: recognize the patterns.**
GuardDuty findings reach EventBridge directly, Security Hub Findings - Imported fires on every finding for the fully automatic path, and Security Hub Findings - Custom Action fires only when an analyst clicks a custom action, which is the human-in-the-loop path.

**Wrong answer A: auto-remediate everything.**
Wiring Findings - Imported to a Lambda that terminates any flagged instance turns a single false-positive finding (the 2.4 pen-tester) into an auto-termination of production, a denial of service against yourself. Fully automatic plus high blast radius plus untested is an outage, so you test in non-prod, enable automatic per control, and gate destructive actions behind a custom action.

**Wrong answer B: use an automation rule to isolate.**
A Security Hub automation rule cannot isolate an instance, because automation rules only modify the finding record in ASFF (severity, workflow status, suppression, notes). Acting on the resource needs EventBridge to Lambda or SSM. This is the high-yield trap.

**Wrong answer C: one admin Lambda with hardcoded credentials.**
An over-permissioned remediation role is a fresh attack surface, and hardcoded credentials in a Lambda is the 2.3 mistake. Remediation roles are least-privilege and scoped to the exact actions, and cross-account remediation uses `sts:AssumeRole` into a scoped member-account role, never shared static credentials.

**The correct pipeline.**
An EventBridge rule matches precisely on the finding type, Workflow Status NEW, and Sample false. A target SSM Automation runbook (preferred for standardized infra actions, many prebuilt as `AWS-*` and `AWSConfigRemediation-*`) or Lambda (for custom logic) performs the exact 2.1 isolation under a least-privilege role. A close-the-loop step sets the finding to RESOLVED or NOTIFIED to prevent re-trigger loops, publishes to SNS, and logs to CloudWatch. Destructive actions sit behind a custom action so an analyst reviews the Detective scope first, with an optional `aws:approve` step inside the runbook.

## The subtle one: automation rules versus EventBridge, and blast-radius control

Several tested edges here.

**Automation rules change the finding, EventBridge changes the resource.** An automation rule can only edit ASFF fields (severity, workflow status, suppression, notes), so any question about acting on the resource (isolate, encrypt, revoke, snapshot) is EventBridge to Lambda or SSM, and reaching for an automation rule is the trap.

**Fully automatic destructive remediation is a self-inflicted outage.** A false-positive finding auto-terminating production is the failure mode, so you filter samples, scope by tag and account, test in non-prod, enable automatic per control, and gate destructive actions behind a human-triggered custom action.

**Remediation is least-privilege and cross-account by AssumeRole.** The remediation role is a high-value target, so it is scoped to the exact actions, and cross-account work uses `sts:AssumeRole` into a scoped member-account role, never hardcoded or shared static credentials.

**Close the loop to avoid re-trigger loops.** Setting the finding to RESOLVED or NOTIFIED after remediating stops the pipeline from firing on its own aftermath.

**ASR is the named solution.** When the question is "remediate common findings consistently across the org," Automated Security Response on AWS is the prebuilt, standards-aligned (CIS, FSBP, PCI DSS, NIST SP 800-53), multi-account answer, the remediation cousin of the 2.2 forensics orchestrator, with automatic rules disabled by default per control.

## Exam relevance

- **Automation rules change the finding (ASFF fields), EventBridge to Lambda or SSM changes the resource.** Acting on a resource is always EventBridge.
- **The three event paths:** `GuardDuty Finding`, `Security Hub Findings - Imported` (automatic), and `Security Hub Findings - Custom Action` (human-in-the-loop).
- **Fully automatic destructive remediation on unfiltered findings is a self-inflicted outage.** Filter Sample false, scope by tag and account, test in non-prod, and gate destructive actions behind a custom action.
- **Prefer SSM Automation runbooks (many prebuilt) for standardized actions, Lambda for custom logic**, under a least-privilege role.
- **Cross-account remediation uses `sts:AssumeRole` into a scoped member-account role**, never hardcoded or shared credentials.
- **Close the loop:** set the finding to RESOLVED or NOTIFIED, notify via SNS, log to CloudWatch.
- **ASR (formerly SHARR) is the named, deployable, multi-account, standards-aligned remediation solution**, the cousin of the Automated Forensics Orchestrator.
