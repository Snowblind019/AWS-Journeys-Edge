## What I built

- Saw what AWS does **automatically** when a key leaks (the `AWSCompromisedKeyQuarantineV2` policy) and why it is not remediation.
- Built the **wrong answers first**: deleting the user, deactivating only the key, and trusting the quarantine, and proved each is insufficient.
- Ran the **correct sequence**: contain the key, eradicate live sessions with an explicit deny, investigate via CloudTrail, hunt and remove persistence, and recover by rotating or migrating to a role.

The point was that a leaked IAM key is an eradication problem, not a containment one. AWS's quarantine only limits damage, deactivating the key does not kill live temporary sessions, and the foothold is rarely a single key, so the real fix is to stop using long-term keys at all.

---

## The model this proves

Responding to a leaked IAM credential is a five-step sequence, and the exam tests where each naive shortcut falls short.

- **AWS's auto-quarantine is damage-limiting, not remediation.** When a key hits a public repo, AWS attaches `AWSCompromisedKeyQuarantineV2`, an explicit deny on a subset of high-risk actions, emails the owner, and opens a support case. Everything the user's own policy allows that is not on the deny list still works.
- **Containment is not eradication.** Deactivating the leaked key or deleting the user does not touch already-issued temporary sessions or any parallel foothold the attacker built.
- **Killing sessions depends on how they were created.**
- **The real fix is to remove the root cause.** Replace the long-term key with a role and temporary credentials.

| Session type | How created | How to kill it |
|---|---|---|
| `AKIA` long-term key | IAM user access key | deactivate or delete the key (blocks new signing only) |
| `ASIA` from `GetSessionToken` (user) | user calls `GetSessionToken` | explicit deny by `aws:userid` (no console button) |
| `ASIA` from an assumed role | `AssumeRole` | role "Revoke active sessions" (`aws:TokenIssueTime`) |
| root-created `GetSessionToken`/`GetFederationToken` | signed in as root | cannot alter, another reason never to use root |

| Step | Action | Why |
|---|---|---|
| Contain | deactivate the leaked `AKIA` key | reversible, stops new signing |
| Eradicate sessions | deny by `aws:userid` (user) or `aws:TokenIssueTime` (role) | deactivating the key does not kill live `ASIA` sessions |
| Investigate | CloudTrail lookup by `AccessKeyId` | scope the blast radius |
| Eradicate persistence | hunt new keys, users, roles, trust changes | a foothold is rarely one key |
| Recover | rotate the key or migrate to a role, then detach quarantine | close the hole and remove the cause |

## What each demo proved

**AWS quarantine: damage-limiting, not done.**
AWS attaches `AWSCompromisedKeyQuarantineV2` within minutes of a leak, showing in CloudTrail as `invokedBy: AWS Internal`, but it is an explicit deny on only a subset of high-risk actions. With it attached, `s3 cp` of the victim's secrets still succeeds if the user's policy allowed S3 reads, which proves it is damage-limiting. It also stays attached until you remove it, so you do not detach it before rotating the key and eradicating persistence.

**Wrong answer A: delete the user.**
Deleting `github-deployer` is blunt, can break legitimate automation sharing the user, and does nothing to a parallel foothold if the attacker already assumed a role or created a second user. Containment is not eradication.

**Wrong answer B: deactivate the key.**
Deactivating the `AKIA` key blocks new signing with it but does not touch already-issued `ASIA` temporary sessions, which stay valid for up to 36 hours. The key and the sessions it minted are independent, so you must explicitly kill the sessions.

**Wrong answer C: trust the quarantine.**
Covered above: the quarantine is a partial deny, and the data-read path is still open.

**The correct sequence.**
Contain by deactivating the leaked key (reversible, rotate after). Eradicate live sessions with an explicit deny, keyed to `aws:userid` for the user's own `GetSessionToken` sessions or to `aws:TokenIssueTime` for assumed-role sessions, which dynamic evaluation kills within minutes. Investigate with CloudTrail lookup by `AccessKeyId` to scope reads, exfiltration, persistence, and privilege escalation. Eradicate persistence by hunting for what the attacker created, a second access key, backdoor users, new roles, or altered trust policies. Recover by rotating the key or, better, migrating to a role, then detaching the quarantine policy and responding to the support case.

## The subtle one: quarantine is not remediation, sessions outlive the key, and the real fix is no long-term keys

Several tested edges here.

**AWS quarantine is damage-limiting, not remediation.** It is an explicit deny on a subset only, so anything else the user's policy allows still works. "AWS handled it" is always the wrong answer, and you still run the full sequence.

**Deactivating the key does not kill live sessions.** `AKIA` deactivation and `ASIA` session validity are independent. Role sessions have a console "Revoke active sessions" button (the `aws:TokenIssueTime` deny from 2.1), but IAM-user `GetSessionToken` sessions have no button, so you kill those with a deny on `aws:userid`. And you cannot alter permissions for `GetSessionToken` or `GetFederationToken` credentials created while signed in as root, which is another reason never to use root.

**Eradicate persistence, the step people forget.** A foothold is rarely a single key, so hunt for second keys, backdoor users, new roles, and altered trust policies, mapping them to the GuardDuty Persistence, PrivilegeEscalation, and CredentialAccess findings. Remove every artifact, not just the original key.

**The real fix is to stop using long-term keys.** The exam's preferred answer is to replace the IAM user and static key with a role and temporary credentials (IAM Roles Anywhere, OIDC for CI/CD, instance profiles). A leaked 15-minute credential is a non-event, while a leaked `AKIA` is this entire lab.

## GuardDuty IAM finding cheat-set

- **`UnauthorizedAccess:IAMUser/InstanceCredentialExfiltration.OutsideAWS`**: instance-role credentials used from an IP outside AWS, the classic stolen-instance-credentials signal.
- **`UnauthorizedAccess:IAMUser/MaliciousIPCaller(.Custom)` / `TorIPCaller`**: API calls from known-bad or Tor IPs.
- **`UnauthorizedAccess:IAMUser/ConsoleLoginSuccess.B`**: a successful console login from anomalous geographies.
- **`Stealth:IAMUser/CloudTrailLoggingDisabled`**: the attacker covering tracks.

## Exam relevance

- **`AWSCompromisedKeyQuarantineV2` is damage-limiting (an explicit deny on a subset), not remediation.** "AWS quarantined it" is never a complete answer, and you detach it only after rotating and eradicating.
- **Deactivating or deleting the key does not kill already-issued temporary sessions.** Kill user sessions with a deny on `aws:userid`, and role sessions with the "Revoke active sessions" `aws:TokenIssueTime` deny.
- **There is no console button for IAM-user `GetSessionToken` sessions**, and root-created `GetSessionToken`/`GetFederationToken` sessions cannot be altered.
- **Containment is not eradication.** Hunt for parallel footholds (extra keys, backdoor users, new roles, altered trust) and remove every artifact.
- **Investigate with CloudTrail lookup by `AccessKeyId`**, and map compromise to the GuardDuty findings above.
- **The real fix is temporary credentials via roles** (Roles Anywhere, OIDC, instance profiles), not long-term keys.
