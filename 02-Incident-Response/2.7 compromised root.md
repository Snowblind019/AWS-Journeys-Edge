# 2.7 — Compromised Root User

**Domain 2: Incident Response (14%)**
**Companion to:** `scs-c03-lab-2_7-compromised-root.md` (the runnable lab). This file records what was built and *why each result happens*, one level deeper than the lab's terse `Result:` lines.

**Cost:** $0. Everything here is IAM and Organizations, with no charge. The caution is operational, not financial: enabling centralized root access management is an org-wide change, so treat it with real change management and test in a non-production organization first.

---

## What I built

- Built the **wrong answers first**: trying to lock root out with a deny policy or permission boundary, applying an SCP to a management-account root, and revoking the root session with `aws:TokenIssueTime`, and saw why each fails.
- Ran the **correct response** to a compromised root: reset the password, delete any access keys, reset MFA, investigate CloudTrail, and hunt persistence and lockout moves.
- Set up the **durable fix**, centralized root credentials management, so member accounts have no root credentials to steal, and reviewed the task-scoped root session model and the management-account exception.

The point was that root sits above IAM, so you cannot contain it with policies, only credentials. SCPs reach member-account root but never the management account, the response is credential rotation plus a persistence hunt, and the durable fix is to delete member root credentials entirely.

---

## The model this proves

Root is not an IAM principal you can constrain with policy, which changes everything about containing it.

| Principal | Kill sessions or contain with |
|---|---|
| IAM role session | `aws:TokenIssueTime` (Revoke active sessions, 2.1) |
| IAM user temporary session | `aws:userid` deny (2.3) |
| Root user | none of these, credential rotation only |

| Control | Restricts member-account root? | Restricts management-account root? |
|---|---|---|
| IAM identity policy or permission boundary | no | no |
| SCP | yes | no |
| Credential rotation (password, keys, MFA) | yes | yes |
| Centralized root management | yes, deletes the credentials | no |

The correct response is credential rotation plus a persistence and lockout hunt, and the durable fix removes the credentials entirely, after which rare privileged tasks run as task-scoped 15-minute sessions:

| Managed task policy | What the root session may do |
|---|---|
| `root-task/IAMDeleteRootUserCredentials` | delete a member's root credentials |
| `root-task/IAMCreateRootUserPassword` | create a member root login profile (recovery) |
| `root-task/IAMAuditRootUserCredentials` | review root credential status |
| `root-task/S3UnlockBucketPolicy` | delete a locked S3 bucket policy |
| `root-task/SQSUnlockQueuePolicy` | delete a locked SQS queue policy |

## What each demo proved

**Wrong answer A: a deny policy does nothing to root.**
Root sits above IAM identity policies and permission boundaries, so the explicit deny that instantly neutralizes an IAM principal in 2.3 has no effect. You cannot restrict the root user with identity-based policies or boundaries, and root containment is credential-level only. This is the headline.

**Wrong answer B: an SCP only reaches member-account root.**
An SCP constrains a compromised member-account root, and it is the one policy type that does. But SCPs do not apply to the management account at all, including its root, so a compromised management-account root leaves you with password rotation, MFA reset, key deletion, and AWS Support. This asymmetry is a frequent exam target.

**Wrong answer C: `aws:TokenIssueTime` is the wrong tool for root.**
The `AWSRevokeOlderSessions` approach keyed to `aws:TokenIssueTime` targets IAM role sessions, and a root console sign-in is not a role session. Match the tool to the principal: role sessions use `aws:TokenIssueTime`, IAM user temporary sessions use `aws:userid`, and root uses neither, only credential rotation.

**The correct response.**
Reset the root password (which needs control of the root email inbox), delete any root access keys (root should never have them, so any present is a red flag), reset MFA to a fresh hardware device, investigate with CloudTrail filtered on `userIdentity.type = Root` (rare and high-signal), and hunt persistence and lockout moves, most dangerously a changed account email or contact info that locks you out of recovery. Contact AWS Support if you are already locked out.

**The durable fix: centralized root credentials management.**
Enabling trusted access for IAM in Organizations, then `enable-organizations-root-credentials-management` and `enable-organizations-root-sessions`, lets you delete member root credentials and disallow recovery, so new member accounts are created with no root password and no recovery eligibility. An account with no root credentials cannot be rooted. Rare genuine root tasks run as task-scoped 15-minute sessions with one of the five managed policies.

**Detective control: alarm on all root use.**
Because root activity is rare, an EventBridge rule matching `userIdentity.type = Root` wired to SNS surfaces any root sign-in or API call immediately, in both member and management accounts.

## The subtle one: root is above IAM, the SCP asymmetry, and constrained root sessions

Several tested edges here.

**You cannot restrict root with IAM policies or boundaries.** Root containment is credential-level only, so the 2.3 deny trick and the 2.1 session revoke both fail against root. Match the tool to the principal: `aws:TokenIssueTime` for role sessions, `aws:userid` for IAM user sessions, credential rotation for root.

**The SCP member-versus-management asymmetry.** SCPs constrain member-account root but never the management account root, so the management account root is a manual-security problem, the same 4.3 exemption with an incident-response consequence.

**Task-scoped root sessions are still constrained.** Each session is scoped to exactly one task (an unlock-S3 session can do nothing else), requires `sts:AssumeRoot` in the management or delegated admin account, and SCPs, VPC endpoint policies, and other policies remain effective during it. Even a root session is not unconstrained.

**The management account root is the crown jewel.** It cannot be centralized or have privileged actions taken through this feature, so it stays manually secured with hardware MFA, no access keys, locked away, used only for the handful of tasks that truly require it.

## Exam relevance

- **You cannot restrict the root user with IAM identity policies or permission boundaries.** Root containment is credential-level only (password, keys, MFA).
- **SCPs constrain member-account root but never the management account root.** A compromised management-account root leaves rotation plus AWS Support.
- **Match the tool to the principal:** `aws:TokenIssueTime` for role sessions, `aws:userid` for IAM user sessions, credential rotation for root.
- **The compromised-root response** is reset password, delete access keys, reset MFA, investigate CloudTrail on `userIdentity.type = Root`, and hunt persistence, especially a changed account email or contact.
- **Centralized root credentials management deletes member root credentials and disallows recovery**, so an account with no root credentials cannot be rooted. Rare tasks use task-scoped 15-minute root sessions with one of the five managed policies, still bound by SCPs and requiring `sts:AssumeRoot`.
- **The management account root cannot be centralized and stays manually secured.** Alarm on all root use via EventBridge to SNS.
