# 5.4 — S3 Encryption (At Rest and In Transit)

**Domain 5: Data Protection (18%)**
**Companion to:** `scs-c03-lab-5_4-s3-encryption.md` (the runnable lab). This file records what was built and *why each result happens*, one level deeper than the lab's terse `Result:` lines.

**Cost:** about $0. A tiny object, a few KMS calls against the existing 5.1 key, and the bucket is deleted at cleanup.

---

## What I built

- A bucket and a small object.
- Uploaded with no flags to confirm the SSE-S3 default, then with explicit `aws:kms` to confirm SSE-KMS and an `SSEKMSKeyId`.
- Applied a bucket policy that denies any `PutObject` not requesting `aws:kms`, then tested explicit-KMS, explicit-AES256, and header-less uploads.
- Optionally pinned the policy to one specific CMK, then added a separate deny-insecure-transport statement to require TLS.

The point was to separate three things people constantly conflate: at-rest encryption, the *choice* of which at-rest encryption, and in-transit encryption. The most-tested subtlety is how a deny condition treats a request that omits the encryption header.

---

## The model this proves

Three distinct layers, and merging them is the trap.

1. **At rest is automatic.** Since the 2023 change, every new S3 object is encrypted at rest with at least SSE-S3 (AES256), with no flags. There is no way to create a plaintext-at-rest new object.
2. **SSE-KMS is the upgrade** that adds a customer-managed key and an audit trail. It is the envelope encryption from 5.3 performed by S3: `GenerateDataKey` per object, the wrapped key in object metadata, `Decrypt` on GET, with the object or bucket ARN as the encryption context from 5.2.
3. **Enforcement is a bucket-policy concern**, separate from what S3 does by default. You deny the uploads you do not want, and you can also require TLS, which is an in-transit control with nothing to do with SSE.

| Mode | Key | Per-object KMS trail in CloudTrail | When it is the answer |
|---|---|---|---|
| SSE-S3 (AES256) | S3-managed | no | default baseline, no extra control needed |
| SSE-KMS | customer-managed CMK | yes (`GenerateDataKey`/`Decrypt`) | "secure and compliant," key control plus audit |
| SSE-KMS pinned to a key | one specific CMK | yes | "only our approved key" |

That CloudTrail visibility of the KMS calls is what makes SSE-KMS the default "secure and compliant" answer over SSE-S3.

## What each demo proved

**Demo A: default encryption is already on (SSE-S3).**
Upload with no encryption flags and `head-object` returns `AES256`. You specified nothing, yet the object is encrypted. This is the post-2023 baseline, and the exam consequence is direct: treat "an object was uploaded without encryption" as impossible for new objects. Only pre-existing objects in old buckets remain unencrypted.

**Demo B: explicit SSE-KMS.**
Request `aws:kms` with your CMK and `head-object` shows `ServerSideEncryption: aws:kms` plus an `SSEKMSKeyId` ARN. Under the hood S3 did the 5.3 envelope sequence with your CMK, and the resulting `GenerateDataKey` and `Decrypt` calls are now in CloudTrail. That audit trail is the whole reason to prefer SSE-KMS when compliance is in the question.

**Demo C: force SSE-KMS with a bucket policy.**
A `Deny` on `s3:PutObject` when `s3:x-amz-server-side-encryption` is not `aws:kms`. Explicit `aws:kms` succeeds, explicit `AES256` is denied, and a header-less upload is also denied. Adding the `s3:x-amz-server-side-encryption-aws-kms-key-id` condition pins acceptance to a single CMK, which is the answer to "ensure objects are only encrypted with our approved key."

**Demo D: require TLS (encryption in transit).**
A separate `Deny` on `s3:*` when `aws:SecureTransport` is `false`. This is independent of SSE: a fully SSE-KMS object can still be requested over plain HTTP unless you deny it. The `Deny` fires when the condition is true, meaning the request is insecure, while HTTPS requests have `SecureTransport` true and pass.

---

## The subtle one: an absent header counts as "not aws:kms"

The header-less denial in Demo C is the most-tested subtlety, and it is worth being precise about. When `s3:x-amz-server-side-encryption` is **absent** from the request, `StringNotEquals` evaluates to **true**, because an absent key is not equal to `aws:kms`, so the `Deny` fires. The reason this matters: policy evaluation runs on the request **as the client sent it**, before S3 injects its default SSE-S3. So even though S3 would have encrypted the object anyway, a header-less request is judged "not aws:kms" and rejected. This is exactly why the enforce-KMS policy reliably forces callers to request `aws:kms` explicitly instead of letting the default slip through. It is the 4.2 explicit-deny logic acting on an absent condition key.

The TLS statement has its own structural gotcha worth pairing here. The require-TLS `Deny` must list **both** the bucket ARN (`:::BUCKET`) and the object ARN (`:::BUCKET/*`). The bucket ARN covers bucket-level actions like `ListBucket`, and the object ARN covers object actions. Listing only `/*` leaves bucket-level calls unprotected, which is the classic looks-right-but-wrong option. The control is also hard to test from the CLI, because the SDK uses HTTPS by default, so you verify it by reading the policy rather than reproducing a plaintext call. That difficulty is itself a tell: in-transit enforcement is policy-verified, not casually testable.

---

## Exam relevance

- **New S3 objects are always encrypted at rest** (SSE-S3 minimum since 2023). "Uploaded without encryption" is impossible for new objects.
- **SSE-KMS is the secure-and-compliant default** because of CloudTrail audit on the KMS calls and customer key control. It is envelope encryption performed by S3.
- **Enforce SSE-KMS** by denying `PutObject` when `s3:x-amz-server-side-encryption` is not `aws:kms`. An absent header counts as not `aws:kms`, because policy runs before default encryption is applied.
- **Pin to a specific key** with `s3:x-amz-server-side-encryption-aws-kms-key-id` for "only our approved key."
- **Require TLS** with a `Deny` on `aws:SecureTransport` being `false`, listing both the bucket and object ARNs. This is the in-transit control, separate from SSE, and it shows up in SCP form too.
