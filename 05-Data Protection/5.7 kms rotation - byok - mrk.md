## What I built

- Enabled **automatic rotation** on the symmetric 5.1 key with a custom 180-day period, forced an **on-demand rotation**, and confirmed old ciphertext still decrypts.
- Created an **EXTERNAL-origin key**, generated my own 256-bit material, wrapped it with the KMS public key, imported it, and destroyed the local plaintext.
- Created a **multi-Region primary key** and replicated it to a second Region.
- Studied **custom key stores** (CloudHSM and XKS) as a scenario, without building them.

The point was that this subdomain answers two questions: how rotation actually behaves and what it does not fix, and where key material lives on a control spectrum that runs from AWS-managed to never-in-AWS.

---

## The model this proves

Two axes run through everything here.

**Axis 1: rotation transparency and its limits.** Rotation swaps the current backing material and keeps the old material. Old ciphertext still decrypts, because KMS reads which material to use from the ciphertext itself. Nothing is re-encrypted, the key ID, ARN, policy, and alias do not change, and the operation is non-destructive. The limit to internalize is that rotation does not undo a compromise of data that is already encrypted, and it does not touch already-generated data keys.

**Axis 2: the key-material-control spectrum.** Where the material lives and who controls the HSM is the decision most custom-key-store questions turn on:

| Option | Where material lives | Who controls the HSM | Rotation | Tested for |
|---|---|---|---|---|
| Standard CMK (AWS_KMS) | AWS shared KMS HSMs | AWS | automatic plus on-demand | default, cheapest |
| Imported / BYOK (EXTERNAL) | AWS KMS, but you generated it | AWS, you generated | manual (re-import) | key generated outside AWS, fast crypto-shred |
| CloudHSM key store | your CloudHSM cluster | you, single-tenant, still in AWS | manual | "dedicated HSMs we control" |
| XKS (external key store) | external manager, outside AWS | you, fully external | manual | "material never in AWS" |

## Rotation: what it changes and what it does not (the subtle one)

**Automatic rotation** is `enable-key-rotation` with a custom period of 90 to 2560 days (default 365, where the custom period is a 2024 addition). `get-key-rotation-status` shows the flag, the period, and the next rotation date.

**On-demand rotation** is `rotate-key-on-demand`, which forces one now. It works whether or not automatic rotation is enabled, it does **not** change the automatic schedule (the next scheduled date stays put), and the lifetime limit is **25 on-demand rotations per key**. Cost is charged for the first and second rotations' retained material, then capped.

The non-destructive proof: a data key wrapped before rotation still decrypts afterward, because KMS uses the old material automatically and you never specify which material to use.

The tested nuance, and the single most important sentence in the subdomain: **rotating the CMK does not re-encrypt existing data, does not rotate already-generated data keys, and does not help if a data key leaked.** A compromised data key stays compromised, because only new data keys use the new material. If data was exposed, you must re-encrypt it, not just rotate the CMK. Rotation reduces the blast radius of a future compromise of the CMK material, it does not remediate a past one.

Eligibility also matters: **only symmetric AWS-origin keys auto-rotate.** Asymmetric, HMAC, imported, and custom-key-store keys are manual, which means a new key plus an alias update, keeping the old key to decrypt or verify.

## BYOK / imported key material

EXTERNAL origin means you generate the key bytes outside AWS and import them. The use cases are a regulation that requires generating key material in your own HSM, or wanting the ability to delete material from AWS on demand.

The flow: `create-key --origin EXTERNAL` (starts `PendingImport` and unusable), generate 256-bit material, `get-parameters-for-import` returns a one-time RSA wrapping public key plus an import token that ties the wrapped material to this key (both expire in 24 hours), wrap the material with the public key using RSA-OAEP-SHA256, then `import-key-material`. Destroy the local plaintext immediately, which is the whole BYOK security model.

Gotchas that get tested:

- **No automatic rotation.** You rotate by importing new material. On-demand rotation for imported keys exists since 2025 and requires the new material to be in `PENDING_ROTATION` state first.
- **You can set expiration** (`KEY_MATERIAL_EXPIRES` with a date) or no-expiry. If material expires, the key becomes unusable until you re-import the same material, and you must keep a copy outside AWS, because AWS does not retain one.
- **You can delete imported material on demand** (`delete-imported-key-material`) without the 7 to 30 day key-deletion wait, a fast crypto-shred of the material while keeping the key shell. Some compliance regimes prefer BYOK for exactly this.
- **The key shell** (ID, ARN, policies) persists across re-imports, so apps do not change.

## Multi-Region keys

An MRK is a set of keys in different Regions that share the **same key material and the same key ID** (with an `mrk-` prefix). Ciphertext encrypted by the primary can be decrypted by a replica in another Region without a cross-Region call, which is the answer to cross-Region DR and active-active encryption.

Flow: `create-key --multi-region` (primary, `mrk-` prefix), then `replicate-key` to another Region.

Facts to lock in:

- Replicas share the same material and key ID suffix, but have **independent key policies, grants, and aliases**, and rotation is managed from the primary. They are not a single global key, each is a standalone key that happens to share material.
- This is **not** cross-Region replication of data. It is the key existing in multiple Regions so each Region's services can encrypt and decrypt locally.
- Contrast a single-Region key, whose ciphertext can only be decrypted by calling KMS in that key's Region.
- Deletion order: a primary cannot be deleted while replicas exist, so schedule the replicas first.

## Custom key stores (scenario only)

Two ways to keep material outside standard KMS:

- **CloudHSM key store:** material lives in a CloudHSM cluster you control (single-tenant, FIPS 140-2 or 3 Level 3 HSMs). Use when a regulation mandates dedicated HSMs. It runs about $1.45/hour, over $1,000/month, so do not spin one up for study.
- **External key store (XKS):** material lives in an external key manager entirely outside AWS, and KMS proxies crypto operations to it. Use when policy says material may never reside in AWS. If your external manager is offline, AWS cannot perform crypto, so you hold the kill switch.

Both are symmetric only, support **no automatic or on-demand rotation** (manual only), and you own availability and durability of the HSM or external store.

Why the right answer wins, on "material generated and held in HSMs we exclusively control, while still using S3 SSE-KMS": a standard CMK fails because material is in AWS's shared KMS HSMs, BYOK fails because once imported the material resides in AWS KMS so "exclusively control" and "held in our HSMs" is not satisfied, and XKS fits "never in AWS" but is overkill and adds a hard external dependency when the requirement is "HSMs we control" rather than "never in AWS." The **CloudHSM key store** wins, dedicated single-tenant HSMs you control that still integrate with SSE-KMS. Change the requirement to "material must never exist within AWS at all" and the answer becomes **XKS**.

## Exam relevance

- **Only symmetric AWS-origin keys auto-rotate.** Asymmetric, HMAC, imported, and custom-key-store keys are manual.
- **On-demand rotation:** any time, max 25 per key, does not change the auto schedule, works even with auto rotation off.
- **Rotation swaps only the current material**, keeps the old, old ciphertext still decrypts, nothing is re-encrypted, and key ID, ARN, policy, and alias are unchanged.
- **Rotating the CMK does not protect a leaked data key.** Only new data keys use new material, and exposed data must be re-encrypted. The single most-tested rotation nuance.
- **Imported (BYOK) keys:** no auto rotation, can expire (then unusable until re-import), you can delete material on demand for fast crypto-shred, and you must keep a copy outside AWS.
- **Multi-Region keys** share material and key ID across Regions but have independent policies, grants, and aliases. They are separate keys, not one global key, and the primary cannot be deleted while replicas exist.
- **CloudHSM key store** is dedicated HSMs you control, **XKS** is material never in AWS. Both are manual-rotation-only and add operational ownership.
- **Rotation cost** is charged for the first two rotations' retained material, then capped.
