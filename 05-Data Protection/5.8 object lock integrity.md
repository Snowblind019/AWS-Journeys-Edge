# 5.8 — S3 Object Lock, Legal Hold, MFA Delete & Checksums

**Domain 5: Data Protection (18%)**
**Companion to:** `scs-c03-lab-5_8-object-lock-integrity.md` (the runnable lab). This file records what was built and *why each result happens*, one level deeper than the lab's terse `Result:` lines.

**Cost:** about $0. Tiny objects, and the bucket is deleted at cleanup, though cleanup has to wait out the short compliance retention before those versions can be removed.

---

## What I built

- An **Object Lock bucket**, which auto-enabled versioning, then exercised each protection on separate object versions.
- A **governance** retention and proved an admin with the bypass can delete it, a **compliance** retention and proved nobody can (including with the bypass) and that it cannot be shortened, and a **legal hold** and proved it blocks deletion until toggled off.
- Studied **MFA Delete** (root-only, CLI-only) and added a **SHA-256 checksum** to prove integrity verification.

The point was that this subdomain sits on a different axis from the encryption labs. WORM ("can it be deleted or changed at all") and checksums ("is it unchanged") are separate questions from who can access the data or how it is encrypted.

---

## The model this proves

Object Lock is WORM for S3, and it has a strict structure:

- **Versioning is a hard prerequisite.** `--object-lock-enabled-for-bucket` auto-enables versioning, and once Object Lock is on you can never disable it or suspend versioning for that bucket.
- **It protects object versions, not objects.** A plain delete on a locked object just adds a delete marker and leaves the locked version intact underneath. Only a versioned delete is what gets blocked.
- **Two retention modes plus an independent legal hold**, and the governance-versus-compliance split is the crux:

| Control | Who can remove early | Can shorten? | Use for |
|---|---|---|---|
| Governance retention | a principal with `s3:BypassGovernanceRetention` plus the bypass header | yes, with the bypass | accidental-deletion protection with an admin escape hatch |
| Compliance retention | no one, including root | no, extend only | hard regulatory WORM (SEC 17a-4, FINRA, CFTC) |
| Legal hold | anyone with `s3:PutObjectLegalHold` (set OFF) | n/a, no date | litigation holds with no fixed end |

On enabling for an existing bucket: historically this was creation-time only (or a Support request), but AWS now lets you enable Object Lock on an existing **versioned** bucket via `put-object-lock-configuration`. Older exam prep still assumes "creation-time only," so know both, and know that versioning is always the prerequisite.

## What each demo proved

**Demo A: Governance mode, protected with an escape hatch.**
A governance retention blocks an ordinary versioned delete with `AccessDenied`, because the version is WORM-protected. The override needs two things together: the `s3:BypassGovernanceRetention` permission **and** the `x-amz-bypass-governance-retention:true` header (the `--bypass-governance-retention` flag sets it). With both, the delete succeeds. The console adds that header by default, which surprises people who assume the console is the safer path. Governance is accidental-deletion protection with an admin escape hatch, not a hard guarantee.

**Demo B: Compliance mode, absolute.**
A compliance retention blocks the delete even with the bypass, because `BypassGovernanceRetention` does nothing for compliance. There is no override: not the admin, not the root user, not AWS Support can delete before expiry, and the only ways out are to wait out the retention or close the account. It also cannot be shortened, only extended, so an attempt to set an earlier `RetainUntilDate` fails. This is the hard regulatory WORM answer (SEC 17a-4, FINRA, CFTC).

**Demo C: Legal hold, indefinite and independent.**
A legal hold blocks deletion while ON and has no retention date. It stays until someone with `s3:PutObjectLegalHold` sets it OFF, after which the delete works. It is independent of retention, so an object can carry both, and deletion is blocked if either is active. Legal hold is the answer to "preserve this indefinitely for litigation, no fixed end date."

**Demo D: MFA Delete, root-only and narrow.**
MFA Delete adds a second factor to the two most destructive operations: permanently deleting an object version, and suspending versioning. The constraints are all tested. It can only be enabled or disabled by the bucket-owner root account (not an IAM user), only via CLI or API (not the console), it requires versioning, and the request must include the root user's MFA device serial and current code. It is distinct from requiring MFA through an IAM policy `aws:MultiFactorAuthPresent` condition, which is a separate IAM-side control.

**Demo E: Checksums, integrity verification.**
Requesting `--checksum-algorithm SHA256` makes S3 compute and store a checksum you can verify on read with `--checksum-mode ENABLED`. S3 supports CRC32, CRC32C, SHA-1, SHA-256, and the newer CRC64NVME, which is now the default for new uploads. Checksums detect accidental corruption and tampering, which complements Object Lock: integrity asks "is it unchanged," Object Lock asks "can it be changed or deleted at all."

## The subtle one: governance vs compliance, and ETag is not integrity

Two distinctions carry most of the exam weight in this subdomain.

**Governance versus compliance** is the single most-tested split. Governance has an escape hatch (the bypass permission plus the header), compliance has none, not even for root, and compliance cannot be shortened. If a question says "guarantee records cannot be deleted by anyone, including administrators, for seven years," that is compliance. If it says "protect against accidental deletion but allow admins to override," that is governance. The bypass doing nothing against compliance is the exact trap in Demo B.

**ETag is not an integrity hash**, the sleeper trap from Demo E. For a single-part, unencrypted PUT the ETag is the MD5 of the object, but for **multipart uploads or SSE-KMS objects the ETag is not an MD5 of the content**. People reach for ETag as a content hash and it quietly stops being one. The dedicated checksum fields are the correct integrity mechanism, not the ETag.

## Exam relevance

- **Object Lock requires versioning**, protects object versions, and once on cannot be disabled, nor can versioning be suspended.
- **Governance retention is overridable** with `s3:BypassGovernanceRetention` plus the bypass header, and the console adds the header by default.
- **Compliance retention cannot be overridden by anyone, including root**, and cannot be shortened, only extended. The hard-WORM answer for SEC 17a-4, FINRA, and CFTC.
- **Legal hold has no end date**, toggles ON/OFF with `s3:PutObjectLegalHold`, is independent of retention, and blocks deletion if either it or a retention is active. The answer for indefinite litigation holds.
- **MFA Delete is root-only, CLI-only, requires versioning**, and protects version deletes and versioning suspension. Distinct from the IAM `aws:MultiFactorAuthPresent` condition.
- **Checksums** (CRC32, CRC32C, SHA-1, SHA-256, and CRC64NVME as the default) verify integrity, and **ETag is not a reliable integrity hash** for multipart or SSE-KMS objects.
- **Integrity and WORM are different axes:** unchanged versus un-deletable.
