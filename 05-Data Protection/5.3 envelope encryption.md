# 5.3 — Envelope Encryption

**Domain 5: Data Protection (18%)**
**Companion to:** `scs-c03-lab-5_3-envelope-encryption.md` (the runnable lab). This file records what was built and *why each result happens*, one level deeper than the lab's terse `Result:` lines.

**Cost:** about $0. A handful of `GenerateDataKey` and `Decrypt` calls against the existing 5.1 key, nothing meaningfully billed, and no new residue.

---

## What I built

- A file deliberately larger than 4 KB, then tried to encrypt it directly with the CMK to hit the wall.
- Used `GenerateDataKey` to get a data key, encrypted the file locally with `openssl` AES-256-CBC, stored only the wrapped data key and the IV, and destroyed the plaintext data key.
- Recovered the file by asking KMS to decrypt the wrapped data key, then decrypting locally, confirming a byte-for-byte match.

The point was to build the pattern that answers "KMS can't encrypt my data," and to see that it is the exact mechanism every AWS service uses under SSE-KMS. The CMK never touches the bulk data, it only wraps a short data key.

---

## The model this proves

A symmetric KMS CMK has a hard 4 KB (4096-byte) plaintext ceiling on direct `Encrypt`, and no flag raises it. The design intent is that a CMK protects keys, not data. Envelope encryption resolves this: KMS generates a small data key, you encrypt the bulk data locally with that data key, and you store the data key in its CMK-encrypted form alongside the ciphertext. The CMK only ever wraps and unwraps the 32-byte data key, which fits comfortably under 4 KB, while the unbounded AES work happens on your own machine.

Three artifacts end up on disk, and the security rests on which one is absent:

| Artifact | What it is | Safe at rest? |
|---|---|---|
| ciphertext (`bigfile.enc`) | the bulk data, AES-encrypted locally | yes, useless without the data key |
| wrapped data key (`datakey.encrypted`) | the data key, encrypted under the CMK | yes, useless without `kms:Decrypt` |
| IV (`bigfile.iv`) | the AES initialization vector, non-secret | yes, not sensitive |

The one thing that must never persist is the **plaintext data key**. It lives in memory only for the moment of encrypting or decrypting, then it is destroyed. That single discipline is the whole security property: everything left on disk is inert without `kms:Decrypt` on the CMK.

## What each demo proved

**Demo A: the 4 KB wall.**
Direct `kms:Encrypt` on the roughly 13 KB file fails with `ValidationException`, plaintext exceeds 4096 bytes. There is no flag to raise the limit, and that is deliberate. The ceiling forces you toward envelope encryption and keeps CMK usage cheap and auditable, since a 32-byte data key always fits under it.

**Demo B: generate a data key, encrypt locally, destroy the plaintext.**
`GenerateDataKey` with `AES_256` returns three fields: `Plaintext` (the data key in the clear, the sensitive part), `CiphertextBlob` (the same data key wrapped under the CMK, safe to store), and `KeyId` (which CMK wrapped it). Encrypt the file locally with the plaintext data key via `openssl`, with no KMS involvement and no size limit, which is exactly what S3 does behind SSE-KMS at scale. Then unset the plaintext key and delete the file that held it. On disk you keep only the ciphertext, the wrapped data key, and the IV.

If you do not need the plaintext key right now (an encrypt-later pattern), `GenerateDataKeyWithoutPlaintext` returns only the wrapped form.

**Demo C: recover the data.**
Ask KMS to decrypt the wrapped data key, then decrypt the file locally with the recovered plaintext key, and `diff` confirms a byte-for-byte match. The plaintext data key again lives only momentarily in memory. The notable detail: `Decrypt` did not need `--key-id`, because for a symmetric key the CMK identity is embedded in the ciphertext blob and KMS reads it automatically. Your identity still needs `kms:Decrypt` on that CMK, so permissions are checked regardless.

---

## The permission split and Decrypt mechanics (the subtle one)

The two halves of envelope encryption take **different permissions**, and that is a feature. The encryptor needs `kms:GenerateDataKey`. The decryptor needs `kms:Decrypt`. Because they are separate, you can build a write-only role that can seal data but never open it, and a read-only role that can open but not re-seal, which is a clean separation for ingest pipelines and audit boundaries.

Two mechanics that ride along:

- **`Decrypt` without `--key-id`.** For symmetric keys the CMK is named inside the ciphertext blob, so KMS resolves it for you. You can still pass `--key-id` to force a specific key as a safety check, and it is **required for asymmetric keys**, where the ciphertext does not carry the key identity the same way.
- **`GenerateDataKeyWithoutPlaintext`** exists specifically for encrypt-later flows, where a component should be able to produce a wrapped key it cannot itself use until it later calls `Decrypt`.

## How this maps to AWS services

This is the exam's framing, and every one of these is the same envelope pattern you just built by hand:

- **S3 SSE-KMS:** S3 calls `GenerateDataKey` per object (or per bucket with an S3 Bucket Key), encrypts the object with the data key, and stores the encrypted data key in object metadata. On GET it calls `Decrypt`. The encryption context is the object or bucket ARN.
- **EBS:** generates a data key for the volume, stores it encrypted, and the instance decrypts it via the CMK at attach time.
- **Secrets Manager, RDS, DynamoDB:** the same envelope pattern under the hood.
- **S3 Bucket Keys:** the cost-optimization answer. It derives a short-lived bucket-level key so S3 makes far fewer `GenerateDataKey` and `Decrypt` calls to KMS, which lowers KMS charges on high-volume buckets. This is the standard "how do you reduce KMS costs for S3" answer.

## Exam relevance

- **Direct `kms:Encrypt` caps at 4 KB.** Bigger data means envelope encryption, and no flag raises the limit.
- **`GenerateDataKey` returns plaintext plus encrypted** versions of the data key, while **`GenerateDataKeyWithoutPlaintext`** returns only the encrypted one for encrypt-later patterns.
- **The plaintext data key must be destroyed after use.** The whole security property depends on it not persisting.
- **Store the encrypted data key with the data.** It is harmless without `kms:Decrypt` on the CMK.
- **`Decrypt` does not need `--key-id` for symmetric keys** (the CMK is embedded in the ciphertext), though permissions are still checked against that CMK. `--key-id` is required for asymmetric.
- **Encryptor needs `kms:GenerateDataKey`, decryptor needs `kms:Decrypt`.** The split enables write-only and read-only separation.
- **S3 Bucket Keys** reduce KMS call volume and cost on high-traffic buckets.
