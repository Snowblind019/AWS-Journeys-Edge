## The model this proves

Three independent topics share one exam skill, which is to eliminate on a constraint. Macie questions hinge on S3-only plus sampled-versus-full. ACM questions hinge on cost, export, renewal, and Region. In-transit questions hinge on available versus enforced, per service. Each has a small set of disqualifying facts that decide the answer, so the work is learning those facts cold.

## Part 1: Macie (data classification)

Macie is a managed service that discovers sensitive data in **S3 only**, using ML and pattern matching, and reports bucket-level posture (public access, encryption status, sharing). It is the answer to "find where PII, PCI, or credentials live in our S3 estate" and "classify data at scale."

Two discovery modes, and the cost axis decides between them:

- **Automated sensitive data discovery** continually samples objects across all buckets and builds a sensitivity heat-map and per-bucket score. It is cheap because it samples rather than scanning everything, and it is on by default for new Macie accounts. This is the answer when the scenario says continuous, cheap, and "don't scan everything."
- **Targeted sensitive data discovery jobs** let you pick buckets and run a one-time or scheduled full inspection. More thorough, charged per byte inspected. This is the answer when the scenario says "inspect every object for an audit."

Identifiers come in three forms: **managed data identifiers** (100-plus built-in types covering PII, financial, credentials, and multi-country formats), **custom data identifiers** (your own regex plus keywords plus proximity rules for org-specific formats), and **allow lists** (text or patterns to exclude from findings, to cut false positives).

Scope facts that get tested:

- Macie is **S3-only**. It does not classify RDS, DynamoDB, EBS, and so on. "Find PII in our database" is not Macie.
- **Multi-account via Organizations** with a delegated administrator, the same pattern as GuardDuty and Security Hub.
- Findings route to **EventBridge**, then Security Hub or Lambda, for automated remediation.

Why the right answer wins, on the canonical drill ("continuously identify which buckets hold credit-card numbers across 40 accounts, cheaply, without scanning everything"): Athena needs you to already know where the data is and does not classify, GuardDuty is threat detection rather than classification (the common distractor, since both are org-wide security services), and nightly targeted jobs on every bucket work but violate "cheaply" and "without scanning everything." Automated discovery org-wide via delegated admin uniquely satisfies continuous, cheap, sampled, and classifying. Swap "cheaply and sampled" for "must inspect every object for an audit" and the answer flips to a targeted job.

## Part 2: ACM certificate lifecycle

ACM provisions and manages TLS certificates, and the exam tests four properties relentlessly: cost, export, renewal, and Region.

| Property | ACM public certificate | ACM Private CA certificate |
|---|---|---|
| Cost | free, you pay only for resources using it | CA roughly $400/month plus per-cert, expensive |
| Trust | publicly trusted by browsers | internal trust only |
| Export private key | no, usable only with integrated AWS services | yes, exportable for use anywhere |
| Auto-renewal | yes if validation stays resolvable | yes, managed |
| Use with | CloudFront, ELB/ALB/NLB, API Gateway | anything (EC2, on-prem, containers) via export |

Validation: **DNS validation** adds a CNAME once, and ACM auto-renews indefinitely as long as the record stays, which is why it is preferred (renewal needs no human). **Email validation** goes to domain contacts and can require manual action at renewal, which is brittle for automation.

Region placement, the top gotcha: **CloudFront requires the cert in `us-east-1`**, regardless of where the origin or buckets sit, and a cert in the wrong Region simply is not selectable on the distribution. **ALB and NLB require the cert in the same Region as the load balancer.** Certificates are Regional resources, they do not replicate, so provision per Region.

Renewal gotcha: ACM managed renewal for a public cert works only if ACM can revalidate, which DNS validation with the CNAME present makes automatic. If you used email validation, or the cert is **imported** (brought from outside ACM), ACM does **not** auto-renew it, and you must re-import before expiry. "Cert expired despite ACM" almost always means an imported cert or broken validation.

Why the right answer wins, on "TLS on a CloudFront distribution fronting S3 with zero renewal toil": importing a cert fails because imported certs do not auto-renew, provisioning in the origin Region (`us-west-2`) fails because CloudFront needs `us-east-1` and the cert will not attach, and Private CA fails because it is not publicly trusted and costs roughly $400/month for a public site. An ACM public cert in `us-east-1` with DNS validation uniquely satisfies free, publicly trusted, and auto-renewing.

## Part 3: Enforcing encryption in transit, per service

The unifying idea is that in-transit is not one switch. Each service has its own enforcement point, and the tested distinction is **available versus enforced**: supporting TLS is not the same as forcing it.

- **S3** (from 5.4): a bucket policy `Deny s3:*` when `aws:SecureTransport` is `false`, covering both the bucket and object ARNs, and the SCP form for org-wide.
- **CloudFront:** the **viewer protocol policy** (client to CloudFront) set to `redirect-to-https` or `https-only` forces TLS to the viewer, while `allow-all` permits HTTP and is the wrong answer. The **origin protocol policy** (CloudFront to origin) set to `https-only` or `match-viewer` keeps the back half encrypted. Setting the viewer to HTTPS but leaving the origin on HTTP leaves a plaintext back-leg, the classic "looks secure but isn't" trap. **Field-level encryption** encrypts specific sensitive form fields at the edge with a public key, so only the downstream app holding the private key can read them, which protects those fields even past CloudFront. That is the answer to "encrypt only the credit-card field end to end."
- **ALB and ELB:** an HTTPS listener with an ACM cert in the same Region as the LB, a listener rule redirecting `HTTP:80` to `HTTPS:443` so plaintext is never served, and a security policy to restrict TLS versions and ciphers (TLS 1.2 or higher).
- **RDS:** force SSL rather than merely allow it. PostgreSQL uses `rds.force_ssl = 1` in the parameter group, MySQL and MariaDB use `REQUIRE SSL` on the account or the relevant parameter, and SQL Server and Oracle force via a parameter or option group. Enabling TLS support is not enforcing it, so you must force it for non-TLS connections to be rejected.
- **Others worth knowing:** DynamoDB, API Gateway, EFS, and Redshift all support an `aws:SecureTransport`-style condition or a require-SSL setting. The exam expects you to know in-transit can be enforced, not merely available.

## Exam relevance

- **Macie classifies data and is S3-only. GuardDuty detects threats.** Do not swap them.
- **Macie automated discovery (sampled, cheap, continuous) versus targeted jobs (full, per-byte, audit).** The cost and coverage words in the scenario decide.
- **Macie is multi-account via Organizations delegated admin**, and findings flow to EventBridge, then Security Hub or Lambda.
- **ACM public certs are free and publicly trusted, but the private key is not exportable.** Private CA is roughly $400/month, internal trust, and exportable.
- **CloudFront cert must be in `us-east-1`; ALB/NLB cert in the LB's Region.** Certs are Regional and do not replicate.
- **DNS validation auto-renews. Email validation and imported certs do not**, so re-import before expiry.
- **In-transit is per-service and the distinction is enforced versus available:** S3 `SecureTransport` deny, CloudFront viewer plus origin protocol policies (mind the back-leg), ALB HTTP-to-HTTPS redirect plus security policy, RDS `force_ssl`.
- **CloudFront field-level encryption** protects specific fields end to end, past the edge.
