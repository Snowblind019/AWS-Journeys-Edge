# 5.2 — Cross-Account KMS & Encryption Context

**Domain 5: Data Protection (18%)**
**Companion to:** `scs-c03-lab-5_2-cross-account-encryption-context.md` (the runnable lab). This file records what was built and *why each result happens*, one level deeper than the lab's terse `Result:` lines.

**Cost:** about $0. The customer-managed keys are $1/month each, but billing stops the moment you schedule deletion, and the only residue is the 7-day deletion window. The cross-account half needs a second account to observe live; the single-account fallback builds both policies without the live call.

---

## What I built

- In **Account A** (the key owner), a CMK `alias/lab-xacct-key` whose key policy keeps an admin statement plus an `AllowAccountBUse` statement naming account B's `:root` for a subset of actions (`Encrypt`, `Decrypt`, `DescribeKey`, `GenerateDataKey`).
- In **Account B** (the caller), `xacct-caller` carrying an IAM policy that allows those KMS actions on A's full key ARN.
- Ran an encrypt from B against A's key, then broke each side in turn to prove neither alone is enough.
- Single account: encryption-context demos, encrypting under a `tenant`/`purpose` context, proving decrypt requires the exact same context, then scoping decrypt by condition key.

The point was the contrast with 5.1. There, the key policy could stand on its own same-account. The moment you cross an account boundary that stops being true, and on top of the access decision encryption context adds a separate integrity-and-scoping layer.

---

## The evaluation model this proves

Cross-account KMS is an **intersection**, never key-policy-only. For a B principal to use A's key, two independent grants must both be present:

1. A's **key policy** must allow account B (via the `:root` delegation, or B's exact principal).
2. B's **IAM policy** must allow the action on A's key ARN.

This is the exact opposite of the same-account result in 5.1 Demo C, where naming the principal in the key policy alone was sufficient. It is the same both-sides rule you proved for the cross-account assume in 4.4: cross-account is AND.

| Grant present | Cross-account result |
|---|---|
| A's key policy allows B, and B's IAM allows the action | Allowed |
| A's key policy allows B, B's IAM does not | Denied |
| B's IAM allows the action, A's key policy does not | Denied |
| Both allow a management action like `ScheduleKeyDeletion` | No effect cross-account |

Two refinements that only appear cross-account:

- **The key policy is the ceiling (the outer-bound rule).** B's IAM can only grant actions A's key policy permits. If B's IAM allowed `kms:ScheduleKeyDeletion` but A's key policy did not list it, the action still fails. The external IAM picks from underneath the key policy's ceiling, never above it.
- **Only a subset of operations work cross-account at all.** The cryptographic operations plus `DescribeKey` and `GenerateDataKey` are effective across accounts. Management operations like `ScheduleKeyDeletion` granted cross-account simply do not take effect, even if both policies list them.

And the `:root` carryover from 5.1: `444455556666:root` in A's key policy means "delegate to account B's IAM," not a grant to any specific B principal. Same delegation behavior as 5.1, now pointed at a foreign account.

## What each demo proved

**Demo: both sides required.**
A's key policy delegates to account B and B's IAM grants `Decrypt`/`Encrypt` on A's key ARN. The encrypt from B succeeds. This is the canonical cross-account configuration, two policies both saying yes.

**Demo: break either side and it is denied.**
Remove B's IAM policy and the same call fails with `AccessDenied`, even though A's key policy still allows account B. Re-attach it, then instead remove A's `AllowAccountBUse` statement, and it is `AccessDenied` again. Either side missing means denied. Key policy alone is not sufficient cross-account, the direct contrast to 5.1.

**The ARN-not-alias requirement.**
Cross-account calls must use the key's fully-qualified ARN. Aliases in account A do not resolve from account B, because an alias is account-local, so a foreign caller has to name the key by ARN. This is an easy silent failure if you reach for the friendly alias out of habit.

---

## Encryption context: authenticated, not secret

Encryption context is a set of non-secret key-value pairs passed at encrypt time. KMS binds them to the ciphertext as **additional authenticated data (AAD)**, and to decrypt you must supply the same context.

**Demo: exact match required.**
Encrypt under `tenant=acme,purpose=billing`. Decrypting with no context, or with the wrong context (`tenant=globex`), both fail with `InvalidCiphertextException`, even though the key and ciphertext are valid. Decrypting with the exact context succeeds. Order of the pairs does not matter, but keys and values are case-sensitive and must match exactly. The context is authenticated, so a mismatch or an omission fails the decrypt.

The important reframe: encryption context is not confidentiality. It is plaintext, and it is logged in CloudTrail. Its value is integrity binding (the ciphertext is tied to its context) and policy enforceability, not hiding anything.

---

## Encryption context as policy scope (the subtle one)

This is where encryption context earns its keep, and it is the most-tested use. A condition on `kms:EncryptionContext:<key>` scopes a principal's decrypt rights to only ciphertext encrypted under a matching context, without granting blanket decrypt on the key.

In the lab, a statement allows `kms:Decrypt` for role `acme-app` only when `kms:EncryptionContext:tenant` equals `acme`. That role can decrypt acme data on the key but is denied globex data on the **same key**, by condition rather than by a separate key. The related key `kms:EncryptionContextKeys` with `ForAllValues:StringEquals` requires that only certain context keys are present, regardless of value.

Two facts make this a common right answer:

- **AWS services set encryption context for you automatically.** S3 uses the object ARN, Secrets Manager uses the secret ARN. That is exactly why a `kms:EncryptionContext:` condition can pin a single key to a single bucket or secret: the service supplies the context, and the condition matches it.
- **It scopes without proliferating keys.** You can give one key to many tenants and still isolate them by context condition, instead of minting a key per tenant.

---

## Exam relevance

- **Cross-account KMS needs both the key policy (allowing the external account or principal) and the caller's IAM policy.** Neither alone works. Same-account (5.1) can be key-policy-only, and that contrast is the tested distinction.
- **The key policy is the ceiling**, and the external IAM policy grants a subset, never more.
- **Use the key ARN cross-account, not the alias**, because foreign aliases do not resolve.
- **Only crypto plus `DescribeKey`/`GenerateDataKey` are effective cross-account.** Cross-account management actions do not take effect.
- **Encryption context must match exactly to decrypt.** A mismatch or omission is `InvalidCiphertextException`.
- **Encryption context is authenticated, not secret** (it is in CloudTrail). Use it for integrity and policy scoping, not to conceal data.
- **`kms:EncryptionContext:<key>` conditions scope decrypt to specific data**, and AWS services set context automatically (S3 = object ARN, Secrets Manager = secret ARN), which is how a key gets pinned to one bucket or secret.
