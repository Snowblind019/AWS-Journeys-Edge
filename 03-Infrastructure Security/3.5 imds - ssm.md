# 3.5 — IMDSv2 & SSM-Based Instance Management

**Domain 3: Infrastructure Security (18%)**
**Companion to:** `scs-c03-lab-3_5-imds-ssm.md` (the runnable lab). This file records what was built and *why each result happens*, one level deeper than the lab's terse `Result:` lines.

**Cost:** about $0. Instances are pennies, and IMDS settings, roles, and patch baselines are free. If you built the private variant, the three interface endpoints bill hourly per AZ, so delete them promptly.

---

## What I built

- Reproduced the **IMDSv1 SSRF path**: from the instance, an unauthenticated GET to the metadata address returned the full role credentials, which is the entire attack when paired with an SSRF bug in any app.
- Required **IMDSv2** and watched the unauthenticated GET turn into a 401, with credentials now requiring a PUT-for-token first, then locked the hop limit down.
- Set the account default, then saw why a **default is not enforcement**, and stacked the real enforcement layers.
- Replaced the bastion and SSH pattern with **Session Manager** (zero inbound ports, IAM-authenticated, fully logged) and noted **Patch Manager** rides the same channel.

The point was that two hardening moves define this subdomain. Kill the IMDSv1 credential-theft path by requiring IMDSv2, and remove the inbound management surface entirely by using SSM instead of SSH. Both replace a working-but-exposed default with a closed one.

---

## The model this proves

**Axis 1, IMDS credential theft.** The instance metadata service at `169.254.169.254` hands out the instance role's temporary credentials. Under IMDSv1 that is a plain unauthenticated GET, so any SSRF bug in an app on the box lets an attacker make the instance fetch the credentials URL and return the keys. No AWS exploit is involved, just a vulnerable app plus IMDSv1. IMDSv2 closes this by requiring a session token obtained with an HTTP PUT that carries a custom header, and by attaching a low IP hop limit to the response. Two properties defeat SSRF: most SSRF primitives can only issue a plain GET, not a PUT with a header, and the low hop limit stops the token from surviving a relay back out through a reverse proxy or container NAT.

**Axis 2, the management plane.** The old pattern is an inbound SSH port to a bastion, which is an open port, a key to manage, and a host to patch. Session Manager removes all of it: the shell is brokered outbound through the SSM service, authenticated with IAM, and every keystroke is logged to CloudWatch Logs or S3 with CloudTrail audit. Patch Manager rides the same SSM channel, so patching also needs no inbound access.

---

## What each demo proved

**IMDSv1: SSRF yields full credentials.**
From the instance, curling the security-credentials path with no token returns `AccessKeyId`, `SecretAccessKey`, and `Token`, unauthenticated. That is the whole attack: an SSRF bug anywhere in an app on the box turns into full role credentials, with nothing about AWS itself exploited.

**IMDSv2: the path closes.**
Setting `--http-tokens required` makes the old unauthenticated GET return 401. You now must PUT to the token endpoint first (with a TTL header), then present the token on the GET. The hop limit is set to 1 for a plain host, and the two properties above are what make this defeat SSRF rather than merely add a step.

**Session Manager: management with zero inbound ports.**
Remove the inbound SSH rule entirely, attach `AmazonSSMManagedInstanceCore` to the instance role, and connect with `ssm start-session`. No port 22, no bastion, no SSH keys, and every session is IAM-authenticated and logged to CloudWatch or S3 with CloudTrail audit.

**Patch Manager: patching on the same channel.**
Patching rides the SSM channel too, so it needs no inbound access. Define a patch baseline (approved patches and an auto-approval delay), group instances by a patch group tag, and run scans and installs inside a maintenance window, with compliance reported back through SSM.

## Enforcing IMDSv2: a default is not enforcement (the subtle one)

This is where the exam separates a plausible answer from the correct one. `modify-instance-metadata-defaults` sets the account and Region default so new instances inherit IMDSv2, but that is weaker than people assume. The default can be overridden at launch, and it does not touch existing instances. Real enforcement stacks layers:

- **Per-AMI:** `modify-image-attribute --imds-support v2.0` makes instances from that AMI require IMDSv2, with the hop limit auto-set to 2. Amazon Linux 2023 already disables IMDSv1.
- **Non-overridable, org-wide:** an AWS Organizations declarative policy (introduced December 2024) enforces the IMDS default centrally, so member accounts cannot launch IMDSv1 instances at all.
- **Policy conditions:** an SCP or IAM condition `ec2:MetadataHttpTokens = required` denies `RunInstances` for IMDSv1, and `ec2:RoleDelivery = 2.0` makes the API reject any call made with credentials that were obtained via IMDSv1, which is defense in depth even if v1 is somehow reachable.

Three operational traps sit alongside:

- **The hop limit default is 1, which breaks containers.** In ECS or EKS the pod is one extra hop from the host, so a limit of 1 blocks metadata retrieval and you set it to 2. Too high, though, and you reopen the proxy-relay risk.
- **Token retrieval is a PUT to the link-local `169.254.169.254`**, so a host firewall or NACL that blocks egress to that address means no token, and everything using the role breaks.
- **Enforcement does not remediate existing instances.** You still sweep them with `ModifyInstanceMetadataOptions` via Run Command or a script, and Security Hub control EC2.8 flags instances still allowing IMDSv1.

For private-subnet instances, Session Manager needs three interface endpoints, `ssm`, `ssmmessages`, and `ec2messages` (the PrivateLink pattern from 3.2), and missing one fails sessions with an opaque error.

## Exam relevance

- **IMDSv1 plus an SSRF bug leaks the instance role's credentials** with an unauthenticated GET. Requiring IMDSv2 (`http-tokens required`) is the fix.
- **IMDSv2 defeats SSRF** because it needs a PUT-obtained token and attaches a low hop limit that does not survive a relay.
- **Set the hop limit to 1 for a plain host and 2 for containers.** The default is 1, which breaks ECS and EKS metadata.
- **An account or Region default is not enforcement:** it is overridable at launch and does not touch existing instances. Enforce with a per-AMI `imds-support` setting, an Organizations declarative policy, and SCP or IAM conditions (`ec2:MetadataHttpTokens`, `ec2:RoleDelivery = 2.0`).
- **Existing instances still need a sweep**, and Security Hub EC2.8 flags IMDSv1.
- **Session Manager replaces bastion and SSH:** no inbound ports, IAM-authenticated, logged to CloudWatch and S3 with CloudTrail. Private-subnet use needs the `ssm`, `ssmmessages`, and `ec2messages` interface endpoints.
- **Patch Manager uses the same SSM channel**, so patching needs no inbound access.
