# 3.4 — CloudFront Private Origin, WAF & Shield

**Domain 3: Infrastructure Security (18%)**

**Cost:** about $0 if you delete the same day. The WAF web ACL is $5/month prorated hourly plus $1 per rule and $1 per managed group, so pennies for a short lab, and CloudFront and S3 are free-tier-friendly. Shield Advanced was never enabled, so nothing to unwind there.

## What I built

- Built the **wrong answers first**: a public bucket behind CloudFront (works, but the bucket URL is directly reachable, bypassing every edge control), and legacy **OAI** (locks the bucket but cannot scope to one distribution and cannot serve SSE-KMS objects).
- Replaced them with **OAC**: Block Public Access stays on, the OAC signs origin requests as the CloudFront service principal, and the bucket policy grants that principal scoped to one distribution by `AWS:SourceArn`, so the direct path returns `AccessDenied` while the distribution serves 200.
- Added a **WAF web ACL** (managed rule groups, a rate-based rule, a geo-match rule) to the distribution and proved the rate rule blocks a flooding IP.
- Studied **Shield Standard** (free, automatic) versus **Advanced** as a scenario.

The point was that edge protection is a stack: keep the origin private with OAC, filter L7 with WAF, and rely on Shield at L3/L4, and each layer has a specific gotcha that separates the right answer from a plausible one.

---

## The model this proves

Three layers protect a CloudFront-fronted origin, and the exam tests the boundary of each.

**Private origin.** The origin must be private, and all access must funnel through CloudFront. A public bucket defeats this because the bucket URL is reachable directly, skipping WAF, logs, and every edge control.

| | Public bucket | OAI (legacy) | OAC (current) |
|---|---|---|---|
| Origin actually private | no, direct URL works | yes | yes |
| Scope to one distribution | n/a | no, a shared OAI lets any distribution in | yes, via `AWS:SourceArn` |
| Serve SSE-KMS objects | n/a | cannot | yes, with a KMS key-policy grant |
| Signing | n/a | legacy | SigV4 as the CloudFront service principal |

**L7 filtering.** A WAF web ACL on the distribution inspects application-layer requests: managed rule groups for OWASP-style SQLi and XSS and known bad inputs, a rate-based rule to throttle a flooding IP, and a geo-match rule by country.

**L3/L4 DDoS.** Shield Standard is free and automatic on every account for CloudFront, Route 53, and Global Accelerator. Shield Advanced is the paid tier that adds L7 automatic mitigation, the response team, and DDoS cost protection.

## What each demo proved

**Wrong answer A: public bucket, the origin is wide open.**
The site loads through CloudFront, but curling the bucket's S3 URL directly returns 200 and bypasses CloudFront entirely, which means it bypasses WAF, the access logs, and every edge control. "It loads" hid a wide-open origin, which is the trap of testing only the happy path.

**Wrong answer B: OAI, better but gapped.**
OAI locks the bucket to CloudFront, which is an improvement, but it has two gaps the exam leans on. A shared OAI cannot be restricted to a specific distribution, so any distribution using that OAI gets in, and OAI cannot authenticate to SSE-KMS-encrypted objects, so customer-managed-key objects simply will not serve.

**OAC: the correct lock.**
With Block Public Access on, the OAC signs every origin request with SigV4 as the CloudFront service principal, and the bucket policy grants that principal scoped to one distribution by `AWS:SourceArn`. The direct S3 path returns `AccessDenied` while the distribution serves 200. The `AWS:SourceArn` condition pins access to one distribution, which is also what defeats the confused-deputy problem, the same shape as the cross-account and service-principal work in Domain 4.

**WAF: L7 filtering on the distribution.**
For CloudFront the web ACL is scope `CLOUDFRONT` and must be created in `us-east-1`. It carries managed rule groups (Common and Known Bad Inputs), a rate-based rule (threshold 2000, aggregated by IP over a rolling 5-minute window, blocking an IP until its rate drops back under the limit), and a geo-match rule by ISO country code. CloudFront does not use `associate-web-acl` (that API is regional), so you set the web ACL ARN in the distribution config. Flooding one IP past 2000 requests in 5 minutes starts returning 403 from WAF.

**Shield: the DDoS layer.**
Shield Standard already protects the distribution, free and automatic at L3/L4, with nothing to enable. Shield Advanced is $3,000/month on a one-year commitment plus data-transfer fees, and it adds L7 automatic mitigation via a managed rule group in your WAF web ACL, 24/7 Shield Response Team access, DDoS cost protection, and Firewall Manager integration.

## The subtle one: the layer-specific gotchas

Each layer has a gotcha that is exactly where the "more correct" answer hides.

**OAC plus SSE-KMS needs the key policy too.** If the objects are SSE-KMS encrypted, the bucket policy alone is not enough. You must also add the CloudFront service principal to the KMS key policy with the same `AWS:SourceArn` condition, because the decrypt has to be allowed. OAI cannot do this at all. Separately, an S3 bucket configured as a website endpoint cannot use OAC or OAI, it has to be a CloudFront custom origin, which loses the private-origin guarantee, so use the REST endpoint with OAC and a default root object.

**WAF: deploy new rules in Count mode first.** Going straight to Block on the Common Rule Set is the classic way to 403 your own legitimate traffic, so watch the metrics and sampled requests, tune, then switch to Block. Also, WAF inspects only the first 8 KB of the body on CloudFront (64 KB on ALB and API Gateway) by default, so content-based rules can miss payloads past that limit unless you raise it at extra WCU cost.

**Shield Advanced: the response team is gated.** The 24/7 Shield Response Team requires a Business or Enterprise support plan on top of the $3,000. "We subscribed to Shield Advanced so we can call the SRT" is incomplete without the support plan.

## Exam relevance

- **Keep S3 private and force access through CloudFront with OAC**, granting the CloudFront service principal scoped to one distribution by `AWS:SourceArn`. A public bucket behind CloudFront is the wrong answer, since the origin is still directly reachable.
- **OAC over OAI:** OAI cannot scope to one distribution and cannot serve SSE-KMS objects. OAC does both.
- **SSE-KMS objects behind OAC also need the CloudFront service principal on the KMS key policy** with `AWS:SourceArn`. The bucket policy alone is not enough.
- **CloudFront WAF is scope `CLOUDFRONT` in `us-east-1`, set on the distribution** (not `associate-web-acl`). The rate-based rule aggregates by IP over 5 minutes, managed groups cover SQLi/XSS and known bad inputs, and geo-match is by country.
- **Roll WAF rules out in Count mode before Block.** WAF inspects only 8 KB of the body on CloudFront (64 KB on ALB and API Gateway).
- **Shield Standard is free and automatic at L3/L4.** Shield Advanced ($3,000/month) adds L7 mitigation, DDoS cost protection, and SRT access, but the SRT also needs Business or Enterprise support.
- **An S3 website endpoint cannot use OAC or OAI.** Use the REST endpoint.
