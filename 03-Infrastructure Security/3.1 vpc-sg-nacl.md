# 3.1 — Security Groups vs NACLs (Stateful vs Stateless)

**Domain 3: Infrastructure Security (18%)**
**Companion to:** `scs-c03-lab-3_1-vpc-sg-nacl.md` (the runnable lab). This file records what was built and *why each result happens*, one level deeper than the lab's terse `Result:` lines.

**Cost:** about $0. A couple of t3.micro instance-hours, and the VPC, subnet, IGW, security group, NACL, and route table are all free.

---

## What I built

- A minimal reachable setup: a VPC, a public subnet, an internet gateway, a route table, and a **security group allowing SSH from my IP only**, with an instance I could SSH into.
- Established an SSH **baseline**, then broke the connection two ways: once at the **NACL** by omitting the outbound ephemeral rule, and once at the **security group** by stripping egress entirely.
- Ran the two breakages back to back to see opposite results from the same action.

The point was that the entire security-group-versus-NACL distinction reduces to stateful versus stateless, and the fastest way to make it permanent is to remove outbound from each layer and watch one break the connection while the other does not.

---

## The model this proves

Traffic to an instance crosses two independent filters, and both must permit it: the subnet's NACL and the instance's security group. They differ on the one property that decides everything, statefulness.

- A **security group is stateful.** It attaches to the ENI, it has allow rules only, and when it permits an inbound connection the return traffic is allowed automatically. Its outbound rules are never consulted for that response.
- A **NACL is stateless.** It attaches to the subnet, it has both allow and deny rules evaluated in numbered order (first match wins), and it makes an independent decision on every packet in each direction. The return packet of an allowed inbound connection is a brand-new decision, so it needs its own outbound rule.

| Property | Security Group | Network ACL |
|---|---|---|
| Attaches to | ENI / instance | subnet |
| State | stateful, return auto-allowed | stateless, each direction independent |
| Rules | allow only | allow and deny |
| Evaluation | all rules, most permissive wins | numbered order, first match wins |
| Return traffic | automatic | needs an explicit ephemeral rule |
| New / custom default | no inbound, all egress | deny all until you add rules |

---

## What each demo proved

**Baseline: SSH works across both layers.**
The instance is reachable. Inbound passes the default NACL and the SG's SSH rule, and the response passes back out because the default NACL allows all egress and the SG is stateful. Nothing surprising, which is the whole point of a baseline: you change one thing at a time from a known-good state.

**Break at the NACL: statelessness exposed.**
Swap the subnet onto a custom NACL with an inbound SSH allow but no outbound rule. SSH hangs and times out. The request arrives fine, because inbound rule 100 permits destination port 22. The server sends its SYN-ACK back to your laptop on your ephemeral source port (something like tcp/54321), and that response hits the subnet boundary outbound, where the custom NACL has no outbound allow, so it is dropped. The handshake never completes. The NACL does not remember it just let the request in, so the return packet is judged fresh. Adding an outbound allow for the ephemeral range 1024 to 65535 fixes it.

**Break at the SG: statefulness confirmed.**
Restore the NACL, then strip all egress off the security group. SSH still connects, even with zero outbound rules on the SG, because the SG is stateful and the return traffic for a connection it allowed inbound is permitted automatically. This is the exact mirror of the NACL break, and running them back to back is what makes the distinction stick: same action, opposite result.

---

## The subtle one: the ephemeral rule, and what statefulness does not cover

Two nuances carry the exam weight here.

**The missing outbound ephemeral rule is the classic self-inflicted outage.** A custom NACL with the inbound rule but no outbound allow drops all return traffic, because replies go to the client's ephemeral source port. AWS recommends allowing 1024 to 65535 outbound rather than a tight OS-specific range, because NAT gateways and different clients use different ranges (Linux 32768 to 60999, Windows 49152 to 65535). Scope it too tightly and some clients silently break.

**SG statefulness only covers the response to an allowed inbound connection.** It does not cover traffic the instance itself initiates. Stripping the SG's egress did not break inbound SSH, but it does break the box's own outbound, so a `dnf update` or an API call from the instance now fails. The inbound reply and instance-initiated outbound are different directions and different decisions. That is why "removing egress broke my package updates but not my SSH" is a coherent, tested scenario rather than a contradiction.

---

## Exam relevance

- **Security groups are stateful** (return traffic automatic, allow rules only, attached to the ENI). **NACLs are stateless** (each direction independent, allow and deny rules, numbered first-match, attached to the subnet).
- **A packet must pass both the NACL and the SG.** Both must allow it.
- **A custom NACL denies everything until you add rules**, and it needs an explicit outbound ephemeral allow (1024 to 65535) for return traffic. The missing ephemeral rule is the classic broken-connectivity answer.
- **Stripping SG egress does not break the reply** to an allowed inbound connection, but it does break traffic the instance initiates.
- **NACLs are the only place you can write an explicit deny**, since security groups cannot deny. Blocking a specific malicious IP at the subnet edge is the reason to reach for a NACL rather than an SG.
