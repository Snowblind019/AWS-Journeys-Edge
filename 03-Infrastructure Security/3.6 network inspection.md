## What I built

- Built the **cheap layer**: a Route 53 DNS Firewall rule group with a block rule and AWS-managed malware and botnet domain lists, associated it to the VPC, and confirmed a bad domain returns NXDOMAIN so the client never gets an IP.
- Studied **Network Firewall** and **Gateway Load Balancer** as describe-only, since both bill per endpoint hourly plus per-GB and are not worth standing up for a lab.

The point was that this subdomain is about traffic inspection and egress control at different layers, and the exam's core question is which tool does the job, especially "whose engine inspects the packets."

---

## The model this proves

Three tools sit at different points in the inspection path, and the trick is matching each to its job.

- **DNS Firewall** operates at the DNS resolution layer, on the Route 53 Resolver path. It blocks by domain, uses AWS-managed lists for known malware and C2 without you maintaining them, and DNS Firewall Advanced adds detection for DNS tunneling and DGA (algorithmically generated domains) that static lists miss. Because it sits on the resolver, the lookup itself fails and the client never gets an IP to connect to.
- **Network Firewall** is the AWS-managed inspection engine at L3 through L7. It lives in a dedicated inspection subnet, and you rewrite route tables so ingress and egress are forced through its endpoints before reaching the workload, often centralized in an inspection VPC behind a Transit Gateway (the 3.3 hub). Traffic hits a fast stateless rule group (L3/L4 IP and port, and it must handle both directions), and selected flows pass to a slower stateful rule group (Suricata-compatible, packet and flow inspection, domain and SNI filtering, IPS).
- **Gateway Load Balancer** is not an engine. It exists to insert a third-party virtual appliance inline and transparently, using GENEVE encapsulation on port 6081 to hand traffic to a fleet of appliances, with GWLB endpoints inserting that inspection into the traffic path via routing.

| Tool | Layer and job | Engine | Reach for when |
|---|---|---|---|
| DNS Firewall | DNS resolution, on the Resolver path | AWS-managed lists, plus Advanced for tunneling and DGA | block known-bad domains cheaply, C2 and malware |
| Network Firewall | L3-L7 packet and flow inspection in an inspection subnet | AWS-managed, stateless plus Suricata stateful | AWS-managed IDS/IPS, egress filtering, the backstop |
| Gateway Load Balancer | insert a third-party appliance inline via GENEVE | the vendor's engine | you already own or need a specific vendor firewall or IPS |

---

## What each part proved

**DNS Firewall: block at the resolver, cheaply.**
A block rule with AWS-managed domain lists, associated to the VPC, makes a bad domain return NXDOMAIN, so `nslookup` fails and the client never gets an IP. This is the cheap first layer, and the AWS-managed lists cover known malware and C2 without maintenance.

**Network Firewall: the AWS-managed backstop.**
Described, not built. It is the engine that catches what DNS Firewall cannot see, and its two-tier design is the core: the stateless group is fast and must handle both directions, and the stateful group is the Suricata-compatible inspection with domain and SNI filtering and IPS.

**Gateway Load Balancer: bring your own appliance.**
Described, not built. Its one job is inserting a third-party appliance inline via GENEVE, so it is the answer whenever a specific vendor's engine has to inspect the packets.

---

## The subtle one: bypass, the backstop, and "whose engine"

Three distinctions carry the exam weight here.

**DNS Firewall only inspects queries that go through the Route 53 Resolver.** An instance using a hardcoded external resolver like `8.8.8.8`, or connecting to a raw IP, bypasses it entirely. That is exactly why Network Firewall is the backstop, and why egress to external DNS is usually blocked at the network layer, so clients are forced back onto the resolver DNS Firewall watches. This is a defense-in-depth chain, not a single control.

**The block response type matters.** A custom NXDOMAIN or NODATA response is what makes the client treat the domain as nonexistent. Without it, application behavior is less predictable.

**Network Firewall and GWLB are mutually exclusive answers to "whose engine inspects the packets."** AWS-managed points to Network Firewall. An existing or required vendor firewall or IPS points to GWLB. If a scenario names a vendor, it is GWLB, and if it says AWS-managed, it is Network Firewall.

---

## Exam relevance

- **DNS Firewall blocks by domain on the Route 53 Resolver path**, uses AWS-managed malware and C2 lists, and Advanced adds DNS tunneling and DGA detection. Set the block response to NXDOMAIN or NODATA.
- **DNS Firewall is bypassed by external resolvers or raw IPs**, so pair it with network-layer egress control and Network Firewall as the backstop.
- **Network Firewall is the AWS-managed L3-L7 engine:** stateless (both directions) plus stateful (Suricata, domain and SNI, IPS), in a dedicated inspection subnet, often centralized in an inspection VPC behind a Transit Gateway.
- **Gateway Load Balancer inserts a third-party appliance inline via GENEVE on port 6081**, with GWLB endpoints in the traffic path. It is the answer when a specific vendor engine must inspect.
- **Network Firewall versus GWLB is decided by "whose engine":** AWS-managed is Network Firewall, a named vendor is GWLB.
