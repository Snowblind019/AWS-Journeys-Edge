# 3.2 — VPC Endpoints (Gateway vs Interface)

**Domain 3: Infrastructure Security (18%)**
**Companion to:** `scs-c03-lab-3_2-vpc-endpoints.md` (the runnable lab). This file records what was built and *why each result happens*, one level deeper than the lab's terse `Result:` lines.

**Cost:** about $0 if you clean up promptly. A couple of instance-hours, the gateway endpoint is free, and the interface endpoint bills roughly $0.01/hour per AZ plus per-GB, so delete it right after. Remove the bucket-policy deny before walking away or you can lock yourself out from the console.

---

## What I built

- Started from the **wrong answer**: an instance in a private subnet reaching S3 through a **NAT gateway**, which works but pays for NAT and rides S3's public endpoint.
- Replaced it with a free **S3 gateway endpoint**, deleted the NAT, and confirmed S3 still works privately via a prefix-list route.
- Locked it down with **two policies**: an endpoint policy restricting the endpoint to one bucket, and a bucket policy denying any access not arriving through that endpoint.
- Contrasted with an **interface endpoint** for Secrets Manager (an ENI with a private IP, a security group, and private DNS).

The point was that private access to AWS services comes in two shapes, gateway and interface, and pinning a bucket to the VPC takes two locks, the endpoint policy and the bucket policy, the same both-sides shape as the cross-account KMS work in Domain 5.

---

## The model this proves

VPC endpoints give private connectivity to AWS services so traffic never traverses the public internet or a NAT gateway. There are two kinds, and the service determines which you use:

- **Gateway endpoint**, for S3 and DynamoDB only. It works by injecting a managed prefix-list route into your route table, pointing the service's prefix list at the endpoint. It is free. Because it is route-table-based, it does **not** work from on-premises over VPN or Direct Connect (on-prem traffic never touches your VPC route tables) and not across Regions.
- **Interface endpoint**, for almost everything else (KMS, SSM, Secrets Manager, ECR, and so on). It is an ENI with a private IP in your subnet. It has a security group and optional private DNS, it costs per hour per AZ plus per-GB, and because it is a private IP it is reachable from on-premises.

| Property | Gateway endpoint | Interface endpoint |
|---|---|---|
| Services | S3 and DynamoDB only | almost everything else |
| Mechanism | route-table prefix-list route | ENI with a private IP |
| Cost | free | per hour per AZ plus per-GB |
| Security group | n/a | yes, must allow tcp/443 inbound |
| Private DNS | n/a | optional, resolves the normal hostname to the private IP |
| Reachable from on-prem | no | yes |

The other half of the model is the **two-lock pattern** for pinning a resource to the VPC. The endpoint policy governs what can be done through the doorway (which buckets, which actions). The bucket policy with an `aws:sourceVpce` condition requires callers to arrive through that doorway. Neither alone is enough: the endpoint policy does not stop someone reaching the bucket by the public path or another account, and the bucket policy does not restrict what flows through the endpoint. Together they pin the bucket to the VPC, the same doorway-plus-requirement shape as cross-account KMS.

## What each demo proved

**Baseline: NAT to public S3, the wrong answer.**
The instance in a private subnet reaches S3 through a NAT gateway and it works, but the request went out through NAT to S3's public endpoint and back, incurring NAT hourly and per-GB charges and momentarily riding a public service endpoint. For a workload that only needs S3, paying for NAT is the distractor the exam wants you to reject. "It works" is not "it's correct."

**Gateway endpoint: free and private.**
Creating the S3 gateway endpoint injects a prefix-list route (`pl-xxxx` to the endpoint) into the route table. With that route present you can delete the NAT gateway and S3 still works, now via the endpoint, free, and never leaving the VPC. This is the correct answer to "give a private-subnet workload S3 access cheaply and privately."

**Endpoint policy: restrict the doorway.**
A new endpoint defaults to full access (`"*"`). Restricting it to one bucket means other buckets fail through this endpoint. But the endpoint policy only governs what flows through this doorway, it does not stop someone reaching the bucket by a different path.

**Bucket lock: require the doorway.**
A bucket policy deny for anything where `aws:sourceVpce` is not the endpoint means the instance (through the endpoint) works while the laptop or console (public path) gets `AccessDenied`. Combined with the endpoint policy, the bucket is now pinned to the VPC.

**Interface endpoint: the contrast.**
Secrets Manager (and KMS, SSM, ECR, and so on) needs an interface endpoint, an ENI with a private IP. With private DNS enabled, the normal hostname `secretsmanager.us-east-1.amazonaws.com` resolves to the endpoint's private IP, so existing SDK calls work with no code change.

---

## The subtle one: the hard lock, and the interface-endpoint gotchas

Several sharp edges here.

**`aws:sourceVpce` is a hard lock.** It also blocks the console, CloudShell, and any automation not routed through that specific endpoint. Test it before you trust it and keep a break-glass path. Use `aws:sourceVpc` (the whole VPC) when you want to allow any endpoint in the VPC, and `aws:sourceVpce` (one endpoint) when you mean exactly one. Removing the deny before you walk away matters, or you can lock yourself out of the bucket from the console.

**Gateway endpoints do not reach on-premises.** Because they are route-table-based and on-prem traffic never enters your VPC route tables, a hybrid workload that needs private S3 from on-prem uses an interface endpoint for S3, not the gateway.

**Interface endpoints have two forgotten prerequisites.** The endpoint's security group must allow tcp/443 inbound from the consuming subnets, and without it the failure looks like a generic timeout rather than a permissions error. And private DNS requires the VPC to have DNS resolution and DNS hostnames enabled, which is off by default on some custom VPCs.

---

## Exam relevance

- **Gateway endpoints are free and cover S3 and DynamoDB only.** They are route-table-based, so no on-prem and no cross-Region.
- **Interface endpoints cover almost everything else**, are an ENI with a private IP, cost per hour per AZ plus per-GB, need an SG allowing 443, and are reachable from on-prem.
- **NAT-to-public-S3 works but is the wrong, expensive answer** for private-access and cost questions. A gateway endpoint is the correct one.
- **Pinning a bucket to a VPC takes two locks:** an endpoint policy (the doorway) plus a bucket policy with `aws:sourceVpce` (require the doorway). Same both-sides shape as cross-account KMS.
- **`aws:sourceVpce` is one endpoint, `aws:sourceVpc` is the whole VPC.** Both are hard locks that also block the console, so keep a break-glass path.
- **Interface endpoint failures are usually the missing SG 443 rule or private DNS not enabled** (DNS resolution and hostnames off on the VPC).
