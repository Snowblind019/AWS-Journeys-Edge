# 4.2 — Policy Evaluation Logic

**Domain 4: Identity and Access Management (20%)**
**Companion to:** `scs-c03-lab-4_2-policy-evaluation-logic.md` (the runnable lab). This file records what was built and *why each result happens*, one level deeper than the lab's terse `Result:` lines.

**Cost:** ~$0. One empty S3 bucket and a handful of `GetObject` / `ListBucket` requests (fractions of a cent, inside free tier). Deleted at cleanup.

---

## What I built

- **`lab-user`** — an IAM user with a CLI profile, used as the single principal making every request so the only thing changing between demos is *which policy is in play*.
- **An empty S3 bucket** — the resource. Requests against it (`GetObject` on `bucket/*`, `ListBucket` on `bucket`) are the probes.
- **Three swappable identity policies** (`idget`, `idall`, `ids3ec2`), **two bucket policies** (an allow and an explicit `Deny`), and **one permissions boundary** (S3-only) — attached and detached one at a time.

The point was to run the *same* call repeatedly and watch the allow/deny flip as a single rule changed, so the decision tree stops being a diagram and becomes muscle memory. Each demo isolates exactly one rule.

---

## The evaluation model this proves

Every authorization decision is a walk down one tree. Same-account version:

```
Request
  ├─ Explicit DENY anywhere? ──────────────── yes ─▶ DENY  (final; nothing overrides)
  │     (identity / resource / boundary / SCP / session)
  │ no
  ├─ Boundary set and action not in it? ───── yes ─▶ DENY  (implicit; ceiling)
  │ no / no boundary
  ├─ Allowed by identity OR resource policy? ─ no ──▶ DENY  (implicit default deny)
  │ yes
  ▼ ALLOW
```

Two things the lab makes concrete that the tree alone doesn't:

**Policies are gathered, not read in sequence.** AWS collects *all* applicable documents — identity, resource, boundary, SCP, session — and evaluates them as one set. An explicit `Deny` in any one short-circuits the whole decision before a single `Allow` is considered. The `Deny` living in a different document than the `Allow` is irrelevant; there is no "the allow was closer" logic.

**Same-account is a union; cross-account is an intersection.** This is the single most-tested distinction in the domain.

| Scenario | Rule | What's required |
|---|---|---|
| Same account | Union (OR) | An `Allow` in *either* the identity policy or the resource policy is enough. |
| Cross account | Intersection (AND) | Both the trusting account's resource policy *and* the calling account's identity policy must `Allow`. |

The boundary sits on top of the identity side only: it is a ceiling on what identity-based policies can grant, never a grant itself.

## What each demo proved

**Demo A — implicit default deny, then an identity `Allow` opens it.**
With nothing attached, the call is `AccessDenied` — not because anything denies it, but because nothing allows it. Default is deny. Attaching `idget` (an identity `Allow` on `GetObject`) flips it to success. Establishes rule one: an explicit `Allow` is mandatory.

**Demo B — drop the identity policy, grant via the bucket policy instead → still works.**
Detach `idget` so `lab-user` has zero identity permissions, then put an `Allow` in the *bucket* policy naming the user. The read succeeds with no identity grant anywhere. Same-account union in action: a resource-based `Allow` is sufficient on its own. This is the source of the "user has no identity policy but the call succeeds" exam pattern — look for a resource policy doing the granting.

**Demo C — identity allows `s3:*`, a bucket policy `Deny` on `GetObject` wins, but `ListBucket` survives.**
Attach `idall` (`s3:*`) and add an explicit `Deny` on `s3:GetObject` to the bucket policy. `GetObject` now fails despite the broad identity `Allow` — explicit deny beats any allow. But `ListBucket` still works, because the deny is scoped to the action and resource it names. Explicit deny wins *where it applies*; it doesn't blanket everything. This is the "user has an `Allow` but the call fails" pattern.

**Demo D — identity allows S3 + EC2, a permissions boundary of S3-only caps it.**
Attach `ids3ec2` (S3 and EC2) and a boundary that allows only `s3:*`. The effective permission set is the *intersection*: S3 calls succeed, EC2 calls get `AccessDenied`. The boundary granted nothing — it only lowered the ceiling. Watch for the distractor answer "attach the boundary to give the user EC2"; a boundary never grants.

## Action scope mechanics (the quiet failure mode)

A policy that looks correct can silently fail on ARN shape, and the lab surfaces this because object and bucket actions take different resource forms:

- **`s3:GetObject`** acts on objects → resource ARN must be `arn:aws:s3:::bucket/*` (with `/*`).
- **`s3:ListBucket`** acts on the bucket itself → resource ARN must be `arn:aws:s3:::bucket` (no `/*`).

Swap them and the statement parses fine but matches nothing, so the action falls through to implicit deny. On the exam, a "correct-looking" policy that mysteriously denies is often a `/*`-vs-no-`/*` mismatch on a bucket-level versus object-level action. Worth checking before assuming a missing `Allow`.

---

## Permissions boundary interaction (the subtle one)

A permissions boundary is a ceiling on an entity's **identity-based** permissions only. It does not uniformly cap everything the entity can do, and the edge case is the same one that showed up in 4.1.

Same-account, a resource-based policy that grants directly to a **named IAM user ARN** is **not limited by an implicit deny in a boundary**. So a bucket policy naming `lab-user` directly (the Demo B grant) still works even if the user's boundary omits the action — the resource-based grant stands. The boundary's implicit deny only caps the *identity* path.

The boundary actually bites when:
- the access depends on an **identity-based** grant (Demo D, where S3+EC2 is capped to S3), where the implicit deny caps the user; or
- the boundary carries an **explicit `Deny`** — an explicit deny always wins, even against a directly-named resource-based grant.

One more distinction to keep straight: the named-principal bypass applies to a directly-named **user ARN** (or the role session), **not to a plain role ARN** of the role itself, where an explicit `Allow` within the boundary is still required.

Decision rule: *implicit* deny in a boundary cannot override a same-account resource-based grant to a named user ARN; an *explicit* deny can. A boundary protects you from an over-broad *identity* policy, not from a sloppy *bucket/KMS* policy that names the user directly.

---

## Exam relevance

- **"Has an `Allow` but the call fails"** → look for an explicit `Deny`, or a boundary/SCP that doesn't include the action. The allow being present is a distractor.
- **"No identity policy but the call succeeds"** → a resource policy is granting it. Same-account union.
- **Same-account union vs cross-account intersection** is the most common trap in the domain. Cross-account always needs *both* sides; same-account needs *either*.
- **Boundary is a ceiling, never a grant.** The "attach the boundary to give permissions" option is always wrong.
- **Explicit deny precedence** is the mechanism behind org-wide guardrails (deny `s3:DeleteBucket`, deny actions outside an approved region) regardless of what identity policies allow.
- **Action scope (`/*` vs no `/*`)** for object vs bucket actions is a frequent reason a correct-looking policy denies.
