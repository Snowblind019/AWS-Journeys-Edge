# 4.5 — Federation & IAM Identity Center

**Domain 4: Identity and Access Management (20%)**
**Companion to:** `scs-c03-lab-4_5-federation-identity-center.md` (the runnable lab). This file records what was built and *why each result happens*, one level deeper than the lab's terse `Result:` lines.

**Cost:** $0. Registering an OIDC provider, creating the role, and running `AssumeRoleWithWebIdentity` are all free, and enabling Identity Center to explore is free too. Cleanup deletes the provider and role, so no residue.

---

## What I built

- Registered **GitHub's OIDC provider** in IAM (`token.actions.githubusercontent.com`, client ID `sts.amazonaws.com`).
- Created **`GitHubActionsRole`** with a trust policy federating that provider, conditioned on `aud = sts.amazonaws.com` and `sub = repo:Snowblind019/AWS-The-Hard-Way:*`, with S3 read-only attached.
- Optionally ran a `workflow_dispatch` job that minted an OIDC token and called `sts get-caller-identity`, watching CI receive temporary credentials with zero stored secrets.
- Studied the **Identity Center** model and the rest of the **STS / federation family** as decision drills, since they can't be fully built without an external IdP.

The point was to see that federation is the same trust-policy gatekeeping from 4.1 and 4.4, with one change: the principal is now a federated token instead of an IAM user, so the fence moves from "which ARN is named" to "which token claims are required."

---

## The evaluation model this proves

Federation does not change the model, it changes *who the principal is*. The trust policy is still the gatekeeper. With an IAM principal the trust names an ARN. With web identity the trust names a `Federated` provider, and the real fence is a `Condition` on the token's claims. No claim condition, no fence.

| Identity assuming the role | STS call | Trust principal | The actual gate |
|---|---|---|---|
| IAM user/role, same or cross account | `AssumeRole` | `AWS` (ARN or `:root`) | who is named, plus both sides if cross-account |
| OIDC / web identity (GitHub, Cognito, mobile, EKS IRSA) | `AssumeRoleWithWebIdentity` | `Federated` (OIDC provider) | `Condition` on `aud` and `sub` claims |
| Enterprise SAML 2.0 (Okta, AD FS, Entra) | `AssumeRoleWithSAML` | `Federated` (SAML provider) | trust on the SAML provider, plus `SAML:aud` |
| Existing IAM user needing MFA temp creds | `GetSessionToken` | none (no role) | the user's own creds, plus MFA |
| Custom federation broker (legacy) | `GetFederationToken` | none | a long-lived IAM user / broker |

Everything in this domain is now one gate (the trust policy) with a different lock depending on where the principal comes from.

## What each demo proved

**OIDC end to end, zero stored secrets.**
GitHub presents a signed JWT, AWS validates it against the registered IdP and the role's conditions, and CI gets short-lived credentials. No long-lived access keys living in GitHub secrets, which is the entire reason to do this. The `id-token: write` permission in the workflow is what lets GitHub mint the token. Omit it and the job fails with a confusing "Credentials could not be loaded" that has nothing to do with AWS.

**The `sub` condition is the whole fence (the security lesson).**
If the trust policy checks only `aud = sts.amazonaws.com` and omits `sub`, then every GitHub repository on the internet can present a valid token and assume the role, because `sts.amazonaws.com` is the audience for all GitHub-to-AWS OIDC, not just yours. The `sub` claim (`repo:Owner/Repo:...`) is what binds the role to your repo. This is the most exploited OIDC misconfiguration in the wild, and it answers Checkpoint 1: `aud` proves the token came from GitHub, `sub` proves it came from *your* repo. Scoping runs tightest to loosest:

- `repo:Owner/Repo:ref:refs/heads/main`, only the main branch.
- `repo:Owner/Repo:environment:prod`, only the prod environment.
- `repo:Owner/Repo:*`, any branch, PR, or tag in that one repo.
- `repo:Owner/*:*`, every repo you own, usually too broad.
- no `sub` condition, anyone's repo anywhere, a critical vulnerability.

**The thumbprint is theater.**
Since July 2023 AWS validates GitHub's OIDC certificate against its own trusted CA library, so the thumbprint is not used for validation. The CLI still requires the `--thumbprint-list` argument, so you pass any well-formed value. Don't waste time chasing the "right" thumbprint, and rotations won't break you.

## Cognito: user pools vs identity pools (the perennial trap)

- **User pool** is *authentication*. A directory of app users that returns JWTs saying who you are. It does not grant AWS access on its own.
- **Identity pool** (federated identities) is *authorization to AWS*. It exchanges tokens (from a user pool, Google, Apple, SAML) for temporary AWS credentials via `AssumeRoleWithWebIdentity`, and supports authenticated and guest roles.
- Mnemonic: the user pool authenticates the human, the identity pool gets them AWS creds. A question about letting mobile users upload to S3 directly is an identity pool.

---

## IAM Identity Center: the workforce model

- A **permission set** is a template. When you assign it to an account, Identity Center provisions an IAM role named `AWSReservedSSO_...` in that account. SSO access is still role assumption underneath, meaning temporary creds and no IAM users.
- **Identity source** options: the built-in Identity Center directory, an external SAML IdP (Okta, Entra ID), or AWS Managed Microsoft AD.
- Enabling Identity Center is a **console action**, not a CLI/API one. Once on, `aws sso-admin` and `aws identitystore` work.
- An assignment is (user or group) plus (account) plus (permission set). The user signs in once at the portal, picks an account and role, and gets temp creds.
- **Trusted identity propagation** flows the user's real identity into services like Athena, Redshift, and QuickSight, so access and audit tie to the human rather than a shared role.

That answers Checkpoint 2: 40 accounts with one login and central de-provisioning is Identity Center, not a SAML IdP wired into each account by hand. Direct SAML-to-IAM (a SAML provider plus roles in every account) still works and still appears on the exam, but it is per-account toil. Identity Center is the modern default for workforce access across many accounts: one place for assignments, central de-provisioning, one portal. Reach for direct SAML-to-IAM only for a single account or a legacy constraint.

## Exam relevance

- **Pick the STS call by the identity.** IAM principal goes to `AssumeRole`. OIDC, mobile, GitHub, and Cognito go to `AssumeRoleWithWebIdentity`. Enterprise SAML goes to `AssumeRoleWithSAML`. An existing IAM user wanting MFA temp creds goes to `GetSessionToken`. A custom broker (legacy) goes to `GetFederationToken`.
- **Checkpoint 3 worked:** (a) a Lambda reading another account's bucket is `AssumeRole`, (b) a React Native app with Google sign-in uploading to S3 is `AssumeRoleWithWebIdentity` via an identity pool, (c) employees signing in through Okta to the console is `AssumeRoleWithSAML`.
- **OIDC trust with only `aud` and no `sub`** is the critical-vuln answer. The fix scopes `sub` to your repo, branch, or environment.
- **Cognito:** the user pool authenticates, the identity pool authorizes to AWS. Mobile upload to S3 is the identity pool.
- **Many accounts, central workforce access and de-provisioning** is Identity Center, not per-account SAML.
- **Federation and CI both want temporary creds via a role**, never long-lived access keys stored in the client. This is the secure-by-default through-line from 4.1.
