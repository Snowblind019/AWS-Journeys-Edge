# 4.6 — Attribute-Based Access Control (ABAC)

**Domain 4: Identity and Access Management (20%)**
**Companion to:** `scs-c03-lab-4_6-abac.md` (the runnable lab). This file records what was built and *why each result happens*, one level deeper than the lab's terse `Result:` lines.

**Cost:** $0. Standard SSM Parameter Store parameters and IAM are free. Cleanup deletes the user, role, and parameters, so no residue.

---

## What I built

- Two **SSM parameters**, `/lab/alpha` and `/lab/beta`, each tagged with a `project` key.
- **`abac-user`**, an IAM user carrying its own tag `project=alpha`.
- One **ABAC policy** granting `ssm:GetParameter` on `/lab/*` only when `aws:ResourceTag/project` equals the policy variable `${aws:PrincipalTag/project}`.
- **`AbacRole`** carrying that same policy, with a trust policy that lets `abac-user` both assume the role and tag the session, to prove the federation path where the attribute arrives as a session tag.

The point was to replace "one policy per team that names their resources" with one policy that compares attributes, so onboarding a team becomes a tagging operation instead of a policy edit.

---

## The evaluation model this proves

ABAC changes the authorization question. The earlier labs asked "is this principal named or allowed for this resource." ABAC asks "do the principal's attributes match the resource's attributes, evaluated at request time." The policy is static and free of resource names. The variable is the attribute pair, and the single most important mechanic is **where the principal attribute comes from**.

| Principal type | `aws:PrincipalTag/*` source | Does the role's own resource tag count? |
|---|---|---|
| IAM user | the user's own tags | n/a |
| Assumed-role session | session tags passed at `AssumeRole` (`sts:TagSession`) | No, never |
| Federated session (SAML / OIDC) | IdP attributes mapped to session tags at federation | No |

The policy variable `${aws:PrincipalTag/project}` resolves at request time against whatever populated the principal's tags. That is exactly why the source matters: get the source wrong and the match silently fails even though the policy reads correctly.

---

## What each demo proved

**Demo A: principal tag from the user's own tags.**
`abac-user` is tagged `project=alpha`. It reads `/lab/alpha` (resource `project=alpha`) and is denied `/lab/beta`. One policy, no resource names, automatic isolation. Onboarding a "gamma" team means creating gamma-tagged parameters and a gamma-tagged user, and the policy is never touched. That flat policy count as teams grow is the whole value proposition.

**Demo B: attributes from session tags (the federation pattern).**
Same policy on `AbacRole`, but the attribute now arrives at assume time as a session tag. Assume with `--tags Key=project,Value=beta` and the identical role reads `/lab/beta` while being denied `/lab/alpha`. The role's permissions are fixed, the attribute is dynamic per session. Swap "session tag" for "SAML attribute from Okta" and you have enterprise ABAC: the IdP injects the user's department or project into the session, and one role serves everyone with per-person scope. This is where 4.5 and 4.6 join up.

The gotcha that defines the subdomain: if you instead tag `AbacRole` itself with `project=beta` and pass no session tag, the assume succeeds but `GetParameter` is denied for everything, because a role's own resource tags never populate `aws:PrincipalTag`. Only user tags or session tags do. Tagging the role does nothing for ABAC.

For role chaining, mark a session tag transitive (`--transitive-tag-keys project`) so the attribute survives the next hop. Otherwise it is dropped and the match fails downstream.

---

## Tag-write control is the security boundary (the subtle one)

ABAC trusts the tag, so the right to set the tag is the right to grant yourself access. This inverts where you look for risk: the ABAC policy itself is usually clean, and the real boundary is who can write tags.

- **Self-tagging.** If `abac-user` can run `iam:TagUser` on itself, it re-tags to `project=beta` and reads the other team's data immediately (Checkpoint 1). Deny `iam:TagUser` and `iam:UntagUser` on self.
- **Session tagging.** `sts:TagSession` is a distinct authorized action. The trust policy needs it alongside `sts:AssumeRole`, and so does the caller's identity policy, or `--tags` is rejected and the assume fails (Checkpoint 2). `sts:AssumeRole` alone lets you become the role but not attach attributes. Restrict who can pass session tags and which keys they can set.
- **Resource tagging.** Gate creation and re-tagging with `aws:RequestTag/<key>` and `ForAllValues:StringEquals aws:TagKeys`, so resources can't slip in untagged or be re-tagged into another tenant. An SCP that denies changes to the `project` tag is a common org-wide guardrail on top.

Two silent-failure traps that ride along with this:

- **Tags are case-sensitive in conditions.** `Project` is not `project`, `Alpha` is not `alpha`. A case mismatch is a silent deny, and a classic "the policy looks correct but fails" exam item.
- **Not every service supports `aws:ResourceTag`** for every action. S3 *objects*, for example, use the service-specific `s3:ExistingObjectTag/<key>`, not the global key. Check the service's condition-key table before assuming ABAC works.

---

## ABAC vs RBAC

RBAC scales by adding policies and roles per job function. ABAC scales by adding tags, so the policy count stays flat. AWS recommends ABAC for large, fast-growing, or multi-tenant environments for exactly that reason, while RBAC is fine when roles are few and stable. Real systems mix both. This is Checkpoint 3: a SaaS isolating one workload per customer in a shared account, without a role per tenant, is ABAC, and the per-request `tenant` attribute comes from a session tag mapped from the authenticated tenant's identity (a Cognito or SAML attribute). Adding a tenant is a tagging operation, not a new role.

---

## Exam relevance

- **The `${aws:PrincipalTag/x}` equals `aws:ResourceTag/x` pattern** is the signature ABAC answer to "scale access without writing a policy per team or tenant."
- **Principal tags come from user tags or session tags, never a role's own tags.** The favorite distractor is "tag the role to grant it tag-matched access."
- **Session tags carry IdP attributes** into the decision (`sts:TagSession`, transitive tags for chaining). This is the bridge from federation to ABAC.
- **Tag-write control is the security boundary.** Self-tagging or an unrestricted `RequestTag` is privilege escalation, and a "how is this user escalating" question is often answered by an unguarded tagging permission.
- **Silent failures:** case-sensitive tag values, and service-specific keys like `s3:ExistingObjectTag` in place of the global `aws:ResourceTag`.
